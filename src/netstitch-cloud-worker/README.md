# NetStitch Cloud Worker

Cloudflare Worker + D1 backend contour for community cloud sync.

Cloudflare-facing resources should use a visible `netstitch-*` name, for example
`netstitch-sync` for the Worker and `netstitch` for D1. D1 table names stay short
inside the database and do not need a `netstitch_` prefix.

This module is intentionally separate from the desktop runtime:

- `migrations/` contains D1 schema migrations.
- `src/worker.js` contains the Worker entrypoint.
- `wrangler.example.toml` is a safe tracked example without live database ids.

Live Cloudflare values belong in ignored local config/env files and must not be committed.

## Local Checks

```powershell
scripts\check_cloud_worker.ps1
```

## D1 MVP

The first migration creates:

- auth tables for cloud users, sessions, clients and client keys;
- app catalog populated from authenticated upload payloads;
- public aggregate observations;
- per-author observation rows for `app_id + author_user_id` scoped downloads;
- quota windows, replay cache, submissions and audit tables;
- retention indexes for bounded cleanup of rows older than 365 days.

## Observation Tags

- `GET /v1/tags?query=<substring>` lists globally discoverable tag text with `user_count`; an authenticated response also marks the caller's namespace with `is_own` and returns the account usage count.
- Tags enter the caller's namespace only through an authenticated, ES256/JWT-verified observation upload. Direct tag creation and rename endpoints are intentionally absent; authenticated `POST /v1/tags/delete` removes only the caller's associations.
- Tags are canonical upper-case ASCII `[A-Z0-9._-]`, at most 16 characters. All whitespace and non-English characters are rejected. Limits are 100 active tags per account and 32 distinct tag texts per logical observation.
- `/v1/apps` and `/v1/observations` accept a `tag` substring filter. Migration `0015_observation_tags.sql` adds `user_tags` and `observation_tags`; `0016_uppercase_tags.sql` canonicalizes existing values and enforces the upper-case format. Expired orphan tags are released by bounded cleanup.

## Upload Auth

Upload requires both:

- `Authorization: Bearer <session_token>` from the Google OAuth browser/device flow;
- `x-netstitch-jwt: <ES256 compact JWT>` signed by the active client key.

The JWT must use `typ = JWT`, `alg = ES256`, `kid = <client key id>`, audience
`netstitch-cloud`, scope `observations:append`, TTL no longer than 15 minutes,
`iss = netstitch-client:<client_id>`, `sub = <client_id>`, unique `jti`, and
`body_sha256` matching the raw request body.

## Google OAuth Auth

The active auth path is Google OAuth/OIDC with a browser/device polling flow:

- desktop calls `POST /v1/auth/google/start` with `client_identifier`, a client
  public key, and the current UI language;
- Worker creates a one-time `oauth_states` row and returns a browser URL plus
  `poll_secret`; the intermediate browser pages are rendered in that UI language;
- browser page verifies a server-issued SVG captcha generated by the Worker,
  runs an invisible browser-verification workload, redirects to Google with
  PKCE/state, and callback stores the issued NetStitch session in D1;
- desktop polls `POST /v1/auth/session/poll` and stores only the returned
  NetStitch session plus the locally generated client private key, both protected
  by Windows DPAPI until explicit sign-out.

Required Cloudflare secrets/vars for live OAuth:

- var `NETSTITCH_GOOGLE_CLIENT_ID`;
- secret `NETSTITCH_GOOGLE_CLIENT_SECRET`;
- var `NETSTITCH_GOOGLE_REDIRECT_URI` matching the Google OAuth application;
- secret `NETSTITCH_IDENTITY_PEPPER` for HMAC hashing Google subject/email
  identity values before they are stored in D1;
The captcha and browser-verification gate use the same applicable policy as the
referenced `ingame.shin0by.com` flow:
digits from `23456789`, length `6`, SVG segmented glyphs with decoy/noise
layers, TTL `300s`, minimum solve time `5s`, max `3` attempts per challenge,
and a refresh pool of `6` challenges per OAuth state with round-robin rotation.
The generated artwork is stored as a `10 x 3` set of SVG tile data URIs and the
browser page assembles those tiles with JavaScript, micro-delays, tiny overlap and
subpixel jitter so there is no single inline image in the initial HTML. The auth
page keeps the captcha flow in one compact column, shows the answer field at the
same width as the captcha, provides an icon-only refresh action that reloads the
current OAuth page to issue the next server challenge, and opens a blurred zoom
overlay with a 3x captcha preview on captcha click. The browser page does not
contain a Google OAuth URL before captcha verification. After captcha submit, the
Worker verifies the challenge, marks the D1 `oauth_states` row as `captcha_ok`,
and returns the server-generated Google OAuth URL only as a `302 Location`
redirect. Challenge answers are stored only as salted SHA-256 hashes in D1.

Before the Google redirect, the browser also solves a state-bound verification
challenge: SHA-256 proof-of-work, `seeded-memory-walk-v1` with `128 KiB` and
`2` rounds, canvas/WebGL/storage/language/timezone/screen/Worker/timing signals,
and a light interaction trail. Pointer coordinates inside the submit button are
sent as percentages and treated as a strong risk signal when missing, exactly on
0/100% edges, corners, or an implausibly perfect center. This is risk scoring,
not a standalone hard fail, so keyboard or assistive flows can still pass unless
combined with other hostile automation signals. Browser-verification challenges
are one-time, TTL-bound, and bound to the OAuth state.

Password-based `/v1/auth/register` and `/v1/auth/login` are not exposed by the
Worker. NetStitch does not accept user passwords in the cloud auth path.
