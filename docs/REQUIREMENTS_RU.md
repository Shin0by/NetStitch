# Требования NetStitch

## Назначение

`NetStitch` разрабатывается как локальное desktop-приложение для сбора IP-адресов, к которым обращаются выбранные пользователем процессы, с подтверждением наблюдений и передачей выбранных локальных данных внешним portable-модулям интеграции.

## Утверждённый стек

- Язык: Rust
- Desktop UI: Dioxus Desktop
- Привилегированный backend мониторинга: embedded Rust watcher runtime внутри основного desktop-приложения
- Хранение данных: SQLite
- Первый этап: Windows и базовый Linux monitoring backend; macOS остаётся отдельным backend-этапом
- Общий desktop shell: кроссплатформенный native executable

## Базовые функциональные требования

- Проект должен поддерживать развитие как non-web desktop приложения.
- До первого стабильного релиза проект не должен сохранять obsolete aliases, compatibility routes, старые CLI-имена или временные shim-контракты только ради обратной совместимости с промежуточными dev-версиями. Если принято более правильное имя, структура или API-контракт, старый вариант удаляется в той же работе, документация и тесты переводятся на новый вариант. Исключение возможно только после явного решения пользователя для уже опубликованного release.
- Пользователь должен иметь возможность выбрать один или несколько `exe`/исполняемых файлов для наблюдения.
- Известные приложения должны добавляться через внешний runtime-контракт `.app`; конкретные приложения описываются данными манифеста, а не отдельными ветками core-кода.
- Portable-сборка должна поддерживать пользовательские runtime-коннекторы через папку `apps/*.app` рядом с `NetStitch.exe`, чтобы пользователь мог добавить, удалить или отключить коннектор без перекомпиляции.
- Если папка `apps/` существует рядом с exe/cwd или явно задана через `NETSTITCH__CONNECTORS_DIR`, она считается активным пользовательским набором коннекторов. Если внешних `.app` файлов нет, NetStitch не создаёт их при запуске и не включает встроенный fallback known-app список; пользователь остаётся в manual add flow.
- Формат runtime-коннектора должен быть документирован в source `resources/connectors/apps/README_RU.txt` / `resources/connectors/apps/README_EN.txt` и в portable shipped-файлах `apps\README_RU.txt` / `apps\README_EN.txt`, поддерживая минимум: `id`, `display_name`, `process_names`, `process_aliases`, `discovery_sources`, `discovery` rules и `enabled = false`.
- Каждый known-app коннектор обязан проектироваться сразу кроссплатформенно: manifest должен описывать приложение как продукт, а не только Windows exe.
- Каждый коннектор должен знать свой `connector_id`, display name, платформенные process aliases и правила поиска приложения на ПК через доступные для ОС источники: Windows стандартные каталоги/App Paths/Store-MSIX/root-path discovery/строковые значения реестра, macOS `.app` bundles и Linux `.desktop`/Flatpak/Snap/PATH.
- Если для новой платформы пока нет runtime monitoring backend, её connector metadata всё равно должна добавляться в `.app` manifest при создании или изменении known-app connector.
- Shipped known-app manifests для Discord, Telegram, WhatsApp, Google Chrome, Mozilla Firefox и Yandex Browser являются редактируемыми `.app` файлами, которые поставляются packaging/install flow. Rust known-app modules внутри `src/netstitch-connectors/src/modules` допустимы только как source/dev/test contour и не подменяют отсутствующие runtime `.app`.
- Если коннектор обнаружил приложение на ПК, оно должно добавляться в `Tracked apps` в режиме `disabled`, без автоматического запуска мониторинга.
- Пользовательские runtime-коннекторы могут описывать разные logical apps или профили с одним и тем же executable path. Такие записи должны различаться по `connector_id` и отображаться отдельными строками `Tracked apps`; ограничение `один exe_path = одно приложение` допустимо только для manual add flow, где пользователь явно добавляет тот же путь повторно.
- Runtime snapshot должен отдавать диагностический блок по коннекторам: сколько connector-managed приложений реально найдено по существующим `exe_path`, и какие сохранённые `Tracked apps` сейчас указывают на отсутствующий executable. UI обязан выводить в footer `Message` одноразовый статус успешной/пустой загрузки коннекторов и недоступных приложений только при стартовой загрузке списка текущего запуска; этот блок не является live watcher файловой системы и не должен повторно логировать статусы приложений на каждом snapshot refresh.
- Коннектор не должен терять уже существующее enabled/disabled состояние `Tracked apps`. Для connector-managed приложений с versioned-папками, например `Discord\app-*`, bootstrap должен оставлять одну строку продукта: переносить её на самую новую найденную версию executable и удалять stale-строки старых версий вместе с их наблюдениями, чтобы в списке не появлялось несколько Discord.
- В списке `Tracked apps` вручную добавленные приложения должны отображаться сверху по новизне добавления, а все приложения, найденные коннекторами, должны быть внизу списка и сортироваться по алфавиту display name.
- Пользователь должен иметь возможность исключить приложение из активного списка `Tracked apps`; это действие останавливает дальнейший мониторинг приложения и убирает его из активного списка, но не удаляет уже полученные monitoring observations из SQLite. Уже полученные данные не принадлежат lifecycle удаления приложения: только пользователь отдельным явным действием решает удалить конкретные observations или выполнить destructive purge, если такой режим будет введён. Historical observations должны оставаться пригодными для CSV export, cloud upload policy и будущего анализа.
- Удаление приложения из `Tracked apps` должно выполняться только после явного подтверждения в modal-окне с вопросом и вариантами `Yes` / `No`; клик по `X` не должен сразу удалять данные.
- Новая SQLite БД не должна содержать пользовательские приложения по умолчанию. Даже если на машине найдено приложение по пользовательскому connector manifest, оно добавляется только через явное действие пользователя или через connector discovery flow, где найденные connector-managed приложения стартуют выключенными.
- UI должен иметь bulk-переключатель для всех tracked apps в виде такого же compact switch, как в строке приложения, с лейблом `Enable all` слева; label должен использовать тот же основной цвет текста, что и label switch-а `Web localhost` в header. Этот switch работает как overlay `ui.enable_all_overlay` поверх индивидуальных `tracked_apps.enabled`, сохраняется в SQLite `app_settings`, включает все приложения для отображения и мониторинга, но не переписывает индивидуальные флаги в БД, поэтому после отключения overlay возвращаются ранее включённые вручную приложения; отладочная кнопка переключения первой строки не допускается в пользовательском интерфейсе.
- Desktop UI должен иметь tray menu с пунктами `Показать/Скрыть окно`, `Скрывать в свёрнутое`, `Web сервер`, `Запоминать положение`, `Начать/Остановить сканирование` и `Выход`. Одинарный клик по tray icon ничего не делает, двойной клик показывает окно.
- Desktop UI должен выполнять неблокирующую проверку последнего GitHub Release для NetStitch. Если версия release выше текущей версии приложения, включая увеличение только revision-сегмента, кнопка `Информация` в header подсвечивается зелёным. В окне `Информация` при наличии обновления footer показывает активную голубую кнопку `Обновить программу`, которая открывает страницу GitHub Release/Downloads в системном браузере. Если версия совпадает, release metadata недоступна или проверка завершилась ошибкой, кнопка `Информация` остаётся обычного цвета, а автоматическая загрузка, установка или запуск внешних файлов не выполняются.
- Desktop UI не должен запускать второй экземпляр под той же Windows-учётной записью. Повторный запуск `NetStitch.exe` должен тихо найти уже открытое окно, показать/восстановить его из свёрнутого или скрытого состояния и вывести на передний план, не показывая отдельный message box и не создавая второй runtime.
- Галка `Запоминать положение` должна сохраняться в SQLite `app_settings` как `ui.remember_window_placement`. При включённой галке UI обязан сохранять геометрию окна и hidden-state в ключи `ui.window_x`, `ui.window_y`, `ui.window_width`, `ui.window_height`, `ui.window_hidden` только при штатном завершении приложения; при следующем старте восстанавливается геометрия, но окно всегда открывается видимым, даже если прошлое завершение сохранило `ui.window_hidden=true`. Hidden-state используется только для restore/show flow внутри текущей tray-сессии, а не для cold start. При выключенной галке tray-показ обязан центрировать окно и возвращать его к минимальному размеру.
- Все остальные приложения должны добавляться через стандартный manual path flow: пользователь явно указывает путь к исполняемому файлу.
- Если поле manual path пустое, кнопка `+` должна открывать native file picker для выбора executable; этот picker должен быть модальным относительно текущего UI-окна NetStitch; если поле заполнено, кнопка `+` должна добавлять указанный путь только если его ещё нет в `Tracked apps`.
- Поле manual path в `Tracked apps` должно быть компактным, иметь placeholder `Path`, лёгкую встроенную кнопку-крестик для очистки содержимого и внешнюю кнопку `+` той же высоты без отдельной кнопки `Browse`; кнопка `+` должна использовать общую плоскую control-палитру без засветов и объёмных эффектов, центрировать иконку по X/Y; панель `Tracked apps` должна иметь явный header со стабильной UI-сущностью; header должен использовать отдельный цвет из project palette, не иметь отступов от панели сверху и по бокам, а также не иметь собственного верхнего и боковых бордеров; заголовок панели должен быть примерно на 30% меньше стандартного `card h2`; пояснение `Add executable paths or toggle apps in the shell state.` должно быть доступно как CSS-tooltip круглой иконки `?` рядом с заголовком на hover/focus, а не зависеть от native `title` и не занимать отдельную строку панели.
- Система должна сохранять путь к приложению, `pid`, `remote IP`, `remote port`, протокол, время первого/последнего обнаружения и счётчик обращений.
- Система должна фиксировать состояние сетевой попытки (`attempting / established / closing / failed`) и счётчики `failed_hits`/`successful_hits` для каждого наблюдаемого endpoint.
- Desktop UI должен поддерживать CSV export/import для выбранных строк `Monitoring`: экспорт пишет те же столбцы, что таблица мониторинга (`Application`, `IP`, `Domain`, `Port`, `Protocol`, `Connection`, `Requests`, `First seen`, `Last seen`), а импорт добавляет данные в SQLite как реальные наблюдения без очистки текущей таблицы. Уникальность импортируемых строк определяется по `remote IP + remote port + protocol`; повторный импорт такого же endpoint обновляет накопленные времена/счётчики, а новый endpoint добавляется отдельной строкой, чтобы пользователь мог собрать мониторинг из нескольких CSV перед единым экспортом через внешний модуль.
- Header-фильтр `Домен` должен применяться к текущим и новым строкам `Monitoring` в desktop и browser shell, поддерживать обычный поиск подстроки без `*` и wildcard-режим с `*` как любым числом символов, например `*example.com` и `example*.com`; tooltip поля обязан объяснять этот синтаксис.
- Обычные текстовые поля ввода во всём UI не должны менять watcher-owned состояние, фильтры или запускать тяжёлые действия на каждый введённый символ. Значение фиксируется по `Enter`, `change`/потере фокуса или явной кнопке действия; на `Enter` поле проигрывает стандартную короткую pulse-анимацию. Поля с конечным набором значений остаются `select`/switch и применяются сразу по смене значения.
- В overlay экспорта через интеграцию раздел `Дополнительные настройки` должен поддерживать ручной ввод доменов и кнопку `Добавить`, которая переносит недублирующиеся доказанные домены из выбранных строк `Monitoring` в поле `Домены`. Такие домены используются только после явного `Применить`, нормализуются и дедуплицируются модулем без записи module-owned данных в основную SQLite БД.
- `Применить` в `Дополнительных настройках` не должен писать внешние файлы: он только фиксирует текущие дополнительные настройки как готовые к следующему `Анализ` или `Экспортировать`. `Анализ` обязан выполнять dry-run того же сценария, что и экспорт, но без записи на диск. `Сброс` очищает дополнительные настройки и отделён от `Закрыть` в footer оверлея.
- Оверлей `Дополнительные настройки` должен иметь вертикальную компоновку: панель настроек сверху на всю ширину окна, чтобы длинный `Шаблон правила` был читаемым, а панель `Не покрыто правилами профиля:` снизу занимает оставшееся пространство.
- Система должна асинхронно обогащать найденные IP адреса WHOIS/range ownership metadata через linked native network tool library. Возможность enrichment может быть отключена через `ip_enrichment.enabled`; основной мониторинг, snapshot, desktop UI и browser shell не должны блокироваться из-за DNS/WHOIS, timeout или сетевой ошибки enrichment. Поле `Domain` заполняется embedded watcher runtime только из payload-level `http_host`, `tls_sni` или `quic_sni`; CSV import может восстановить домен как доверенное пользовательское наблюдение. Runtime snapshot должен отдавать диагностический статус domain-capture path, чтобы отличать отсутствие HTTP Host/TLS/QUIC SNI от отказа packet backend или невозможности сопоставить пакет с tracked app.
- Native network tool module должен быть полноценным гибким сетевым модулем: предоставлять native shared-library ABI для runtime-вызовов embedded watcher-а, принимать network probe targets от caller-а, не содержать встроенный список endpoint targets и не зависеть от UI для выполнения `lookup`, `lookup-domain`, `probe-endpoint` и `once` library actions. Action `probe-endpoint` является единственным каноническим именем проверки доступности endpoint target и поддерживает `host:port` плюс опциональный protocol-prefix `protocol://host:port`, IPv4, bracketed IPv6 и домены, например `udp://1.1.1.1:53` или `tcp://example.com:443`; дополнительные имена для этой операции не допускаются, потому что проверка не является DNS-only.
- Embedded watcher runtime должен оставаться узким модулем мониторинга/API внутри `NetStitch.exe`: фоновые enrichment/probe задачи выполняются через linked native network tool library и сериализуются общим runtime lock, чтобы одновременно не выполнялось больше одного сетевого tool-call.
- Desktop UI запускает watcher runtime внутри основного процесса. Локальный machine-readable control surface, если он понадобится позже для automation/headless сценариев, должен быть новым явно документированным app-owned entrypoint-ом в native-only runtime lifecycle.
- endpoint probe targets для UI-managed диагностики должны поставляться внешним editable файлом `config\endpoint_probe_targets.txt` или override-переменными `NETSTITCH__ENDPOINT_PROBE_TARGETS` / `NETSTITCH__ENDPOINT_PROBE_TARGETS_FILE`; entries поддерживают `host:port` и `protocol://host:port`, а desktop/browser UI передают embedded watcher runtime в snapshot-запросе и `endpoint_probe_target`, и `endpoint_probe_protocol`.
- Таблица `Monitoring` показывает `Application`, `IP`, `Domain`, `Port`, `Protocol`, `Connection`, `Requests`, `First seen`, `Last seen` и `Action` без отдельной колонки публичности IP. Доменный поиск учитывает `domain`, `owner`, `range`, `registry` и `source`. Header панели `Monitoring` показывает switch `Публичные`: включено показывает только публичные IP, выключено - только непубличные IP; состояние switch сохраняется в SQLite `app_settings` с ключом `ui.monitoring.public_ip`. Footer панели `Monitoring` показывает счётчики строк `Строк`, `Отображено` и `Выбрано`. Значения доменов отображаются как однострочный input-like/path-field, чтобы длинные строки можно было прокрутить без расширения таблицы.
- Список `Ignored addresses` должен показывать доказанный домен для адреса/базового IP правила, если такая информация есть в кеше с источником `http_host` или `tls_sni`, иначе выводить `-`; tooltip `?` должен находиться сразу после адреса и показывать domain/source/owner/range/registry/source, а для localhost/локальных IP или их подсетей дополнительно пояснять, что это локальный/localhost адрес. Такие же enrichment-подсказки должны быть доступны рядом с IP в `Monitoring`.
- SQLite должен хранить `endpoint_domain_cache` для payload-level доменов с `domain_source` и ключом `tracked_app_id + remote_ip + remote_port + protocol`, а также `ip_whois_ranges` для IP-level owner metadata. `ip_domain_cache` используется только для throttle/status metadata enrichment-проходов, а не как источник домена. Если WHOIS диапазон уже известен, принадлежность IP определяется локально из кеша без нового запроса. Таблица диапазонов ограничена разумным максимумом `1000` строк с ротацией старых записей.
- Windows backend должен собирать UDP/QUIC remote endpoints через WinDivert FLOW layer, если доступен WinDivert runtime и процесс запущен с правами администратора.
- Для любых выбранных пользователем процессов, у которых Windows UDP table показывает только локальный socket без remote endpoint, NetStitch должен выявлять фактические remote UDP endpoints через WinDivert FLOW или packet-level fallback. Основной контракт - новые UDP-события после старта мониторинга; уже существующий socket может быть привязан, если после старта через него проходит новый packet/event. Фиксация должна идти по process/PID/app ownership и endpoint tuple, без хардкода конкретных приложений, игр, IP или портов. Полевой пример: игра может держать локальный socket вроде `0.0.0.0:64090` и логировать remote endpoint вида `34.79.201.95:64xxx`, при этом TCP owner tables показывают только отдельные TCP endpoints; NetStitch должен фиксировать UDP `remote IP + remote port + protocol`, если elevated WinDivert contour доступен.
- Runtime snapshot имеет диагностику UDP/FLOW endpoint capture, отдельную от диагностики доменов: backend started/error, число FLOW/packet events до фильтрации, число UDP events, matched tracked-app endpoints, unmatched/dropped events и последнюю понятную ошибку. Если UDP/FLOW недоступен или не видит ожидаемый endpoint, UI/footer diagnostics должны позволять отличить отсутствие админ-прав/WinDivert от ошибки сопоставления PID/tracked app и от отсутствия событий в WinDivert.
- Расширенный мониторинг является отдельной persisted-настройкой `domain_capture.enabled`, выключенной по умолчанию и доступной через switch `Расшир. монитор.` над switch-ом `Web сервер`. Этот режим включает WinDivert FLOW/packet-контур для UDP/QUIC-сокетов и доказанных доменов из HTTP Host, TCP TLS SNI и QUIC Initial SNI. При включении на Windows UI/watcher должны проверить elevated-права процесса; если прав администратора нет или WinDivert backend не открылся, footer `Message` пишет понятную одноразовую ошибку, а switch возвращается в выключенное состояние.
- Embedded watcher runtime должен быть библиотечной частью основного приложения, а не автономной CLI-утилитой. Если продвинутым пользователям понадобится headless/automation-контур, он должен быть новым documented app-owned entrypoint-ом с отдельным security/testing contract.
- Будущий app-owned headless/automation entrypoint, если он будет введён, должен иметь явные actions для запуска/остановки monitoring, управления tracked apps, чтения snapshot и работы с observations внутри основного runtime boundary.
- Community cloud observations должны иметь server-side retention не больше 365 дней: строка endpoint-а (`app_id + ip + port + protocol`) удаляется из D1, если её `last_seen` старше retention cutoff. Это относится только к облачной D1, а локальные monitoring observations остаются под управлением пользователя и не удаляются автоматической cloud retention policy.
- Должен существовать project-owned operator cleanup для облачной D1 с двумя явными областями: `Scope=AppData` удаляет только `app_catalog`, `observations`, `observation_author_rows`, `observation_submissions`, `domain_verifications` (данные приложений, портов, протоколов, доменов и публикаций), сохраняя пользователей, клиентов, сессии, ключи, авторов, auth/captcha/rate-limit/browser-verification states, quota windows и audit rows; `Scope=All` по явному требованию удаляет весь клиентский след: пользователей, идентификаторы клиентов, сессии, ключи, авторов, app catalog, observations, OAuth/captcha/rate-limit/browser-verification states, quota windows, audit/cache rows и любые данные, переданные клиентами. В обоих случаях сохраняются schema/migrations/service metadata, а база остаётся готовой к работе.
- App-owned actions `enable-all` и `disable-all` должны массово включать или отключать tracked apps без привязки к UI-текстам.
- App-owned actions для `ips`, `apps` и `snapshot` должны читать SQLite/core snapshot через embedded watcher runtime.
- App-owned actions `confirm` и `unconfirm` должны поддерживать выбор observed endpoints по id, IP-адресу или всем видимым строкам, включая фильтр `Failed attempts`.
- Action `export` должен экспортировать подтверждённые и ещё не экспортированные IP через generic integration-aware экспортный контур. Design target должен поддерживать отдельные `preview/apply` операции, список изменённых файлов в результате и parity между desktop/browser UI поверх embedded runtime routes.
- Все app-owned automation/headless actions, если они будут введены, должны быть описаны в документации с примерами и типовыми кейсами до использования.
- Пользователь должен иметь возможность подтверждать наблюдения перед экспортом.
- Пользователь должен иметь возможность отфильтровать проблемные адреса через отдельный фильтр `Failed attempts`, чтобы подтверждать их для экспорта до восстановления доступности.
- Пользователь должен иметь управляемый ignore-list адресов: из строки `Monitoring` можно добавить remote IP в список игнорирования, а из панели `Ignored addresses` удалить адрес из списка. Фильтрация должна игнорировать только то, что находится в этом списке, без отдельного switch для localhost. По умолчанию список содержит `127.0.0.0/8`, `::1/128` и обнаруженные локальные IP текущей машины как точные CIDR-правила `/32` или `/128`, чтобы loopback и обращения к собственному LAN-адресу скрывались без ручной настройки. Обнаружение локального IP должно идти по упорядоченному fallback-списку минимум из 8 IPv4 и 8 IPv6 route-probe targets: Google, Cloudflare и другие публичные DNS/anycast endpoints; каждая попытка ограничена `10s`, а в ignore-list можно добавлять только IP, который ОС вернула как локальный source address, после фильтрации loopback/unspecified/multicast/broadcast/documentation и IPv6 transition ranges вроде Teredo `2001:0::/32` и 6to4 `2002::/16`. Панель `Ignored addresses` использует свой header с названием и `?`, без повторного заголовка внутри body; header-иконка `?` этой панели визуально поднята на `2px`; каждый адрес отображается отдельной компактной однострочной row-сущностью с одинаковой шириной колонок: слева фиксированная колонка IP-адреса `230px`, сам адрес выводится светлым основным текстом через общий scrollable `path-field`, чтобы IPv4 помещался полностью, а IPv6/CIDR можно было прокрутить до конца, затем tooltip `?`, домен и стандартная квадратная delete-кнопка `20x20` справа; list-контейнер использует тот же scroll-контракт, padding, top/bottom border и фон, что подпанель `Tracked apps`, а его высота рассчитывается ровно на семь адресных строк: семь tuned-строк, шесть gap, внутренний padding и border; пока данные не подгружены, список показывает семь skeleton-строк без scrollbar. Удаление правила выполняется только через modal-подтверждение; для localhost и локального IP modal обязан показывать отдельное пояснение о последствиях.
- Каждая строка таблицы `Monitoring` должна иметь стандартную square close-кнопку удаления наблюдения в action-ячейке; клик открывает modal-подтверждение, а подтверждение выполняет удаление через core/API и удаляет только выбранный `observed_endpoints` row из SQLite, не затрагивая tracked app и другие наблюдения.
- Список `Ignored addresses` не должен раздвигать панель ниже нижнего края `Tracked apps`: после пяти compact-строк адресов внутри списка появляется собственный вертикальный scroll, а высота строки подгоняется от старой высоты `30px` до текущего tuned-значения так, чтобы ровно пять строк помещались целиком. Правая колонка не использует placeholder-ы и не наращивает внутренние отступы ради выравнивания, а сама панель `Ignored addresses` растягивается на всю ширину своего правого столбца.
- Экспорт должен идти только в безопасный пользовательский слой, выбранный модулем. Основное приложение не должно знать vendor-managed списки конкретного модуля и не должно писать module-owned данные в основную SQLite БД. Прямая правка выбранного профиля допустима только в explicit advanced-режиме модуля, а merge в существующие списки допустим только в explicit dangerous-режиме с отдельным подтверждением и idempotent block markers `NetStitch BEGIN/END`. Backup не создаётся автоматически при экспорте: пользователь запускает отдельную операцию `Create backup`, которая перезаписывает единственную backup-версию всех файлов, которые текущий режим может изменить.
- Экспорт должен классифицировать ссылки из выбранного профиля по роли файла. Основной UI показывает preview/analyze, changed files и warnings через shared DTO, но правила классификации и конкретные пути принадлежат модулю.
- Profile-aware `Экспортировать` не должен снимать выбор с подтверждённых строк `Monitoring`: `is_confirmed` остаётся true, `is_exported` не выставляется автоматически. После успешной записи UI/browser shell обязан автоматически выполнить `Analyze` для того же запроса и заменить preview post-export анализом, чтобы пользователь сразу видел `0` новых IP и уже существующие IP в целевых списках.
- Внешние интеграции должны подключаться через generic module host. На runtime каждый модуль хранится в `integrations/<module>/module.json`, native library (`.dll` на Windows, `.so` на Linux или `.dylib` на macOS) в `integrations/<module>/bin/`, статические UI assets в `integrations/<module>/assets/`, локальную SQLite БД и контент в `integrations/<module>/data/`. Основная БД NetStitch не содержит module-owned данные.
- Export overlay должен открываться через модульную кнопку в панели `Модули` и не должен выполнять экспорт сразу. Overlay должен поддерживать общие режимы `Attach`, `Patch`, `Merge`, preview найденных правил, preview изменяемых файлов, раздел для uncovered `protocol + port` и явное подтверждение dangerous-режима. Desktop и browser shell обязаны иметь одинаковую функциональность, локализацию и визуальный contract overlay.
- Profile-aware export не должен хардкодить конкретные игры, приложения или внешние продукты. Наблюдения сопоставляются с выбранным профилем по `protocol + port`; обычный export/apply записывает только targets, покрытые найденными правилами выбранного profile. `Анализ` обязан показывать статистику без общего блока: группы `Адреса`, `Домены`, `Диапазоны`, разделённые пустой строкой, и только строки `Выбрано`, `Будет добавлено`, `Пропущено`.
- Панель `Модули` должна показывать module buttons с иконкой и tooltip для обнаруженных модулей, поддерживать горизонтальный scroll и сохранять пользовательский порядок в `ui.modules.order`. Нажатие на module button открывает overlay первого уровня, построенный из типовых UI-сущностей NetStitch: panel/header/footer/subpanel/grid/row/path-field/modal/tooltip/button/switch/status-label/value-label/table-column/file-picker/progress-bar. Overlay выполняет тяжёлую filesystem/root validation только после явного действия пользователя.
- Выбранный вручную или полученный из module download root обязан сохраняться только в локальном storage модуля. Основной `app_settings` не хранит module-owned path/state.
- Загрузка provider/content модулем не должна блокировать watcher API: desktop и browser UI стартуют скачивание через неблокирующий `/v1/integrations/download/start` и дальше читают `/v1/integrations/download-progress`. HTTP-загрузка ждёт максимум `30` секунд до первого байта или очередного read, а после получения первого байта ограничивает фактическую загрузку архивного тела `5` минутами.
- Desktop UI должен по умолчанию работать с embedded watcher runtime, а mock-режим допускается только как явный opt-in для отладки.
- Desktop UI при запуске должен показывать окно сразу: первый paint не должен блокироваться bootstrap embedded watcher runtime, SQLite или discovery коннекторов; эти операции выполняются отложенно после появления оболочки окна.
- Header-фильтры `Monitoring` должны быть каноническим watcher-owned состоянием и синхронизироваться между desktop UI и browser shell в обе стороны. Независимые локальные filter-signals в клиентах не допускаются: изменение фильтра в одной оболочке должно попадать в watcher, входить в `snapshot` и автоматически применяться второй оболочкой.
- Browser shell обязан синхронизировать snapshot секционно и без полного repaint при обычных runtime-изменениях. Полный `render()` допустим только для глобальных причин вроде смены локали; обычные изменения monitoring state, export state, tracked apps, ignored addresses, integration state и header filters должны применяться точечно по diff snapshot-секций.
- Desktop UI должен иметь стабильные UI-сущности для автоматизации и тестов: `id`, `data-ui-entity`, `data-ui-action`, `data-ui-key` и аналогичные технические атрибуты не должны зависеть от локализуемого текста.
- Любое user-facing значение, являющееся путём к файлу/папке или похожим длинным filesystem/location значением, должно отображаться через общую UI-сущность `path-field`: однострочное поле не переносит текст на вторую строку, не создаёт общий горизонтальный scroll родительской панели, позволяет прокрутить длинное значение внутри самого поля и поддерживает focus/selection/copy. Для path/value полей с content-width контрактом ширина сначала подстраивается под текст, но не превышает доступную ширину контейнера; если текст длиннее максимума, поле показывает ellipsis, а при focus ellipsis отключается и пользователь может прокрутить значение до конца. Кликабельный вариант обязан использовать `path-field--clickable`, `cursor: pointer`, tooltip и останавливать propagation, если находится внутри кликабельной строки. Запрещено выводить такие значения как обычный `<p>`/`span` с переносом, badge/chip, обрезанную без возможности просмотра строку или отдельную вторую строку статуса, если явно не утверждён другой компонент.
- Цвет значения определяется не типом контрола, а ролью сущности. Если значение имеет собственный видимый ярлык или колонку (`Домен`, `Папка интеграции`, `Провайдер`, `Основной путь`, `Путь экспорта` и аналогичные labelled values), оно должно выводиться основным цветом текста даже при использовании `path-field` или другого shared input-like контракта. Muted-цвет допустим только для второстепенных данных без собственного ярлыка, например для пути приложения в `Tracked apps`, placeholder/help-текста и служебных диагностических строк.
- Панель `Tracked apps` является эталонной UI-сущностью проекта для panel/header/input-box/button/switch/list-row стиля: все панели проекта и их headers должны выглядеть одинаково по высоте, padding, размеру шрифта, цвету, border-поведению и `title-with-help` структуре; все новые панели, заголовки панелей, кнопки, compact controls, tooltip-поведение и row/list сущности того же типа по умолчанию должны повторять её плоскую палитру, скругление `3px`, compact padding/gap, stable ids/actions и `input-box` control contract, если пользователь явно не утвердил другой visual grammar. Если у панели есть глобальное пояснение, оно не занимает отдельную строку и выносится в круглый `?` в header рядом с заголовком. Header панели не должен содержать badge/chip с фоном, рамкой или pill-геометрией; счётчики и статусы справа допустимы только как лёгкий однострочный текст `panel-header-meta`, чтобы не растягивать высоту header.
- Во всём пользовательском интерфейсе не использовать визуальные badge/chip/pill для статусов и счётчиков: такие значения выводятся как обычные label (`header-label`, `panel-header-meta`, `state-label`) без фона, рамки и pill-скругления. Исключение: круглые индикаторы состояния watcher/web server и круглые иконки приложений, потому что это отдельные сущности, а не badge.
- Глобальный header приложения должен содержать рабочую строку мониторинга: фильтр наблюдений, строку поиска, одну toggle-кнопку `toggle-monitoring`, кнопку подтверждения отфильтрованных строк и кнопку экспорта подтверждённых адресов. Toggle-кнопка в состоянии запуска голубая и подписана `Start monitoring`, а в состоянии остановки оранжевая и подписана `Stop monitoring`; две отдельные кнопки Start/Stop в UI не допускаются.
- Desktop UI должен иметь глобальный window layout: системный titlebar окна показывает `NetStitch ver. <version>`, а внутренний фиксированный header приложения остаётся компактной chrome-полосой без видимого названия/описания программы; фиксированный footer и единственная scrollable content-область находятся между ними; header/footer закреплены на месте и используют единую project palette, близкую к Workbench/VS Code dark: плоские тёмные панели, серые бордеры, светло-серый текст и синий accent; основной контент скроллится только внутри центральной области.
- В глобальном header должна быть квадратная icon-only кнопка `Информация`, открывающая overlay `Информация`. Overlay использует общий `modal__header/body/footer`, но header не содержит help-иконку `?`. Внутри body две panel-секции: фиксированная `О программе` с логотипом `resources/branding/images/NetStitch.png`, названием, версией и кликабельной почтой; ниже panel `Информация`, которая занимает весь остаток высоты и прокручивает только свой body. Информационный текст должен быть разбит на группы `Мониторинг`, `Расширенный мониторинг`, `Импорт и экспорт CSV`, `Отслеживаемые приложения` и `Игнорируемые адреса`; пункты внутри групп отображаются компактными текстовыми row-блоками по стилю list-подпанелей. Упоминания внешних интеграций, авторов и репозиториев в `Информация` не выводятся.
- Правый край глобального header занимает вертикальный стек компактных switch-ов: сверху `Расшир. монитор.`, ниже `Web сервер`. `Web сервер` всегда остаётся прижатым вправо как последний control header-а. Если пользователь пытается включить `Расшир. монитор.` без повышенных прав Windows, switch возвращается в выключенное состояние, в footer `Message` пишется понятная ошибка и поверх окна показывается modal-уведомление о необходимости запуска от имени администратора.
- Desktop UI должен задавать минимальный внутренний размер окна `1350x840`, то есть на 50% больше прежнего baseline `900x560`; начальный размер окна не должен быть меньше этого минимума.
- Начальная высота окна должна совпадать с минимальной высотой; сохранённая пользовательская высота допускается только при включённой галке `Запоминать положение`.
- Главное окно должно использовать зафиксированный алгоритм панелей. Верхняя рабочая область всегда состоит из двух колонок равной ширины: слева `Tracked apps`, справа стек `Модули` над `Ignored addresses`; расстояния между колонками и между панелями фиксированы и не используются как скрытый способ добора высоты. Сначала размещается `Модули` как компактная панель фиксированной высоты, под ней размещается `Ignored addresses`, высота которой зависит только от числа видимых строк в её внутреннем списке. Вся оставшаяся высота окна ниже верхнего стека отводится панели `Monitoring`, которая заполняет остаток по высоте, не выходит под footer и не требует глобального scroll окна.
- Опциональный browser UI допускается только как explicit opt-in shell embedded watcher runtime: канонический путь публикации - корень уникального HTTPS-порта `https://<local-ip>:46473/`, без app-name сегмента и без `/web`; доступ включается switch-ом `Web localhost` в глобальном header desktop UI или tray check-item `Web сервер` и сохраняется в SQLite `app_settings` как `web.localhost_enabled`. `/v1/web-url` должен отдавать URL для footer/clipboard с `#web_key=<derived-key>` fragment; fragment не уходит в GET-запрос, browser JS передаёт ключ в `/v1/web-auth` POST-запросом, получает HttpOnly SameSite cookie и удаляет fragment из адресной строки. Если открыть только IP и порт без ключа, browser UI показывает окно ввода ключа. Browser API обязан проверять web-auth cookie, блокировать чужой `Origin`/`Referer`, не публиковать permissive CORS headers и писать audit-события browser remote actions без секретов. Browser UI должен дублировать основные рабочие панели desktop UI (`Tracked apps`, `Ignored addresses`, `Monitoring`, `Модули`) и глобальную строку управления в header, управлять ими через тот же embedded watcher API, поддерживать language selector через external `language/*.ini` + setting `ui.language` и отдавать `/v1/web-url` для footer/clipboard URL.
- В browser UI выбор файлов не должен использовать native browser file input для путей, которые должны относиться к runtime-машине. Окна выбора приложения, profile export target и CSV import/export должны ходить в embedded watcher API и показывать файловую структуру машины, где запущен `NetStitch.exe`; выбранные пути передаются как строки runtime-host filesystem paths.

После `Web server` должен быть отдельный footer label `DNS:` / `DNS:` с таким же круглым индикатором: зелёный, если embedded runtime нашёл первый доступный endpoint target по порядку, красный если успешного target нет; tooltip показывает первый успешный адрес и полный список проверенных DNS addresses со статусами `True/False/Checking`. На startup/bootstrap, snapshot refresh, render path, открытии окна `Информация` и фоновом polling cloud-запросы запрещены; допустим только показ локально сохранённого cache/mirror состояния. Пока overlay открыт, он может автоматически обновлять доступность, лимиты и списки каждые 10 секунд; refresh должен завершаться и не применяться к UI, если вся refresh-операция длится больше `9.5` секунд, чтобы следующий 10-секундный цикл не накладывался старым состоянием; ручной кнопки refresh внутри overlay нет. Upload берёт только строки, выбранные в текущей таблице `Monitoring`, по той же selection-модели, что CSV export. В форме отправки обязательно поле `Никнейм`: это публичный источник/подпись автора публикации, оно не заполняется из Google и не может быть пустым. Допустимые символы никнейма: английские буквы `A-Z`/`a-z`, цифры и `!.@#$%^&*()_+=-~`; максимальная длина `32` символа. Уникальность никнейма case-insensitive: `User`, `user` и `USER` считаются одним ником и не могут принадлежать разным пользователям. UI обязан проверять ник через Worker после debounce `1.5s` и показывать под полем состояния `Никнейм недопустим`, `Никнейм уже занят` или `Никнейм принят`. Server-side denylist обязан отклонять только явно заданные служебные ники в любых регистрах, включая `root`, `admin`, `support`, `system`, `official`, `netstitch`. Никнейм привязывается server-side к конкретной Google OAuth identity через необратимый provider subject HMAC с server-side secret pepper: разные Google accounts считаются разными авторами и могут иметь разные ники, а другой Google-пользователь не может занять уже привязанный ник. Если тот же автор после публикации меняет ник на свободный валидный ник, уже опубликованные в D1 данные должны отображаться и искаться по новому нику; строки наблюдений должны ссылаться на стабильный author identity, а не хранить ник как неизменяемую копию. Google email/display name/raw subject не хранить обратимо в D1/cloud и не использовать как публичный источник; локально для отображения авторизации допускаются только Windows DPAPI-защищённые Google name/email blobs. Все cloud HTTP-запросы UI должны использовать timeout не меньше 8 секунд для refresh/status и более длинный timeout для interactive auth/upload/download операций. Download доступен без регистрации как общий срез по `app_id`; после входа пользователь может сузить download до своих публикаций по `app_id + author_user_id`/public author signature и видеть список приложений, которые публиковал он сам. Ответ `users/me/apps` должен возвращать текущий public author signature для этой сессии; кнопка `Мои публикации` использует его для видимого фильтра `Автор`, а не доверяет только локально введённому нику. Upload доступен только пользователю, вошедшему через Google OAuth в overlay и прошедшему server-side captcha/rate-limit/browser-verification policy. Создание Google OAuth-сессий должно быть ограничено отдельно от лимита неудачных входов: не более 5 стартов за 15 минут для одного client/IP/UA bucket. Browser-verification должен быть привязан к OAuth state, выполняться перед выдачей Google redirect и включать SHA-256 proof-of-work, короткий memory-walk, canvas/WebGL/Worker/timing/interaction signals и pointer percent risk scoring; отсутствие координат, 0/100%, углы или идеально центральный клик являются сильными risk-сигналами, но не самостоятельным единственным hard fail. Наши browser-страницы OAuth до/после Google должны открываться на выбранном языке UI. Пользовательский пароль NetStitch не принимает и не хранит; локально допускаются только безопасные account metadata, DPAPI-защищённый local session/client state и DPAPI-защищённые Google name/email display blobs до явного выхода. Кнопка `Авторизация` блокируется при активной сессии, кнопка `Выход` блокируется без активной сессии и при нажатии удаляет локальные auth/session данные, DPAPI-защищённые Google name/email blobs и obsolete login/password/stay-signed-in keys. Upload/download/refresh могут запускать bounded server-side cleanup устаревших cloud observations, но не должны удалять локальные observations.
- Cloud upload contract должен принимать один batch размером от 1 до 65535 строк. Значение `limit_count = 0` в quota upload/download означает безлимитный режим операций и не должно блокировать UI или Worker. Quota считается по пользовательским операциям, а не по техническим страницам/пачкам: один download с page windows `0-500`, `500-1000`, `1000-1500` списывает одну download-операцию, а один upload, разбитый клиентом на несколько HTTP batch-запросов с общим `operation_id`, списывает одну upload-операцию.
- В Cloud import staging действия `Добавить в мониторинг` и `Экспорт CSV` должны быть неактивны без явно выбранных строк. Пустой выбор не должен трактоваться как `все строки`. Прогресс cloud upload/download отображается через стандартную сущность progress bar сегментами по 500 строк, поэтому 1600 строк дают 4 шага.
- Панель cloud download должна иметь таблицу выбранных cloud-строк с тем же базовым UX, что `Monitoring`: выбрать все видимые, снять весь выбор, выбрать/снять конкретные строки, видимые колонки app/IP/domain/port/protocol/connection/requests/author, cloud-only колонку `Прив.` / `Private` со значениями `true`/`false` и tooltip, что `true` означает приватную строку, а `false` - общую. Публичный cloud download должен отдавать уже агрегированные строки по тому же логическому ключу, что Monitoring/CSV: `app_id + IP + port + protocol`; приватный/author-scoped срез является отдельным cloud namespace и может учитывать тот же endpoint отдельно для владельца. Выбранные cloud-строки пользователь может добавить в локальную таблицу `Monitoring` тем же накопительным storage-path, что CSV import, или экспортировать в CSV файл через существующий CSV export pipeline без очистки текущих monitoring observations. Признак приватности не входит в локальную observation model, MonitoringCsvImportRowDto и CSV-файл; он существует только внутри cloud import/export boundary и staging UI. Browser shell должен повторять desktop cloud-import функциональность только через локальные watcher routes `/v1/cloud/*`; JavaScript веб-страницы не должен выполнять прямые запросы во внешний Worker/Cloudflare URL.
- Панель cloud download/search должна иметь верхние фильтры списка приложений `Приложение`, `Компания`, `Автор` и cloud-owned dropdown `Private` со значениями в порядке `Все`, `Общие`, `Приватные`. Выбранный `Private` scope должен влиять на число строк в колонке `Строк` списка приложений и на последующую загрузку выбранного приложения. `Все` возвращает общие строки и, если пользователь авторизован, приватные строки текущего аккаунта; без авторизации `Все` эквивалентно `Общие`. `Автор` - это публичный ник/подпись автора публикации и отображается в cloud UI именно как автор. Текстовые фильтры верхнего поиска приложений по `Приложение`/`Компания`/`Автор` не должны выполнять запросы во время набора: пользователь применяет значение клавишей `Enter`, после чего поле делает одну короткую pulse-анимацию и запускает server-side поиск через Worker; фильтры нижней таблицы строк `IP`/`Домен`/`Порт`/`Протокол` применяются локально к уже загруженному набору выбранного приложения. Поля с конечным набором значений (`Протокол`, `Private`) должны быть dropdown/select, остальные поля - текстовый поиск. Поле приложения должно показывать autocomplete-варианты: первые `5` подходящих приложений видны сразу, полный список вариантов доступен через scroll, выбор варианта фиксирует `app_id`, а не только display name.
- CSV export должен записывать идентификаторы приложения и подпись происхождения строки, если они известны. CSV import должен восстанавливать эти поля без попытки заменить их текущим локальным приложением: импортированная строка остаётся привязанной к исходным `cloud_app_id`/signature fields, даже если на машине есть приложение с тем же именем, но другой подписью. Upload обязан отправлять confirmed observations из CSV даже без установленного приложения: если подпись не подтверждена локальным verified-приложением, такие строки уходят как `CloudImportUntrusted`, а не отбрасываются и не маскируются под verified.
- CSV export/import и локальные строки monitoring storage не должны содержать публичный ник автора, Google email, Google subject, user id, client id или другие данные пользователя. Авторская подпись используется только в cloud upload payload/catalog/submission metadata и не становится частью локальной observation model.
- В проекте должен сохраняться единый shared/global contour для документации, tooling и verification path.
- SDK внешних модулей должен быть documented как отдельный developer contour в `docs/module-sdk/`: ABI, manifest, UI-сущности, безопасный host context, разрешённые host-команды, storage layout, пошаговая документация создания модулей и два одинаковых примера одного showcase-модуля на Rust и C++. Для каждого примера должны быть tracked исходники и готовые installable-архивы под Windows/Linux; любое изменение исходников примеров или manifest/UI-схемы требует обновления архивов, а локальная Windows portable-копия showcase-модулей для ручной UI-проверки должна обновляться из этих архивов без удаления module-owned `data/`. Module API должен предоставлять только локальные рабочие данные NetStitch и не должен давать автоматизацию cloud upload/download или CSV import/export.
- UI-сущности Module SDK должны иметь централизованные предсказуемые layout-дефолты в desktop и browser renderer-ах: каждая сущность по умолчанию растягивается на доступную ширину (`width = "100%"`, `size = "stretch"`, `min_width = "0"`, `align = "left"`), а `panel`/`subpanel`/`nested_subpanel`/`grid`/`tabs` растут по высоте только по содержимому (`height = "auto"`, `min_height = "0"`, `scroll = "off"`), если manifest явно не задал иное. Активная корневая body-сущность страницы с `size = "fullscreen"` / `"full"` или viewport-размером (`vw`, `vh`, `vmin`, `vmax`) должна управлять layout-ом самого стандартного окна модуля: host применяет к окну размеры, `align`, `margin`, `padding` и `opacity` этой сущности одинаково в desktop и browser shell. `nested_subpanel` должен быть host-owned двухслойной сущностью с тёмной внешней list-поверхностью и более светлой внутренней row-поверхностью в стиле блока приложений, без необходимости задавать цвета в manifest-е.
- UI text input/textarea entity в Module SDK должен включать кнопку очистки только явно через `clear_button: true`; desktop и browser renderer-ы должны одинаково притухлять эту кнопку при пустом, disabled или readonly поле без тяжёлого refresh/update состояния на каждый введённый символ.
- UI table entity в Module SDK должен поддерживать настройки конкретных столбцов через `table_columns`: `text_field: true` включает стандартный ограничивающий текстовый контейнер в ячейках выбранного столбца, а `width`/`min_width`/`max_width`/`align` управляют размером и выравниванием этого столбца.
- UI action/button entity в Module SDK должен рендерить label кнопки в одну строку при штатной ширине, сохраняя предсказуемую высоту строки и позволяя manifest-у управлять шириной через `width`/`min_width`/`max_width`. Несколько actions внутри одной `action_button` сущности по умолчанию рендерятся в один горизонтальный ряд (`button_layout: "row"`); `align` у сущности выравнивает весь ряд, `button_layout: "column"` явно включает вертикальный список. Для одной физической строки из нескольких групп кнопок или смешанных UI-сущностей Module SDK должен предоставлять универсальные `layout_row` и `spacer`: `layout_row.justify` распределяет любые child-сущности (`left`/`center`/`right`/`space-between`), прямые children внутри строки по умолчанию size-to-content и не раздувают высоту родительской панели, а `spacer` забирает свободное место без button-specific layout hacks.
- Module SDK должен позволять динамически включать и отключать action-кнопки через host-owned UI state без дублирования страниц: `set_ui_values` и live `IntegrationHostEvent.event = "ui_values"` принимают ключи `action.<action_id>.enabled` и `action.<action_id>.disabled`, desktop/browser renderer-ы визуально отключают такие кнопки и не отправляют `ui_action` для disabled actions в header actions, `action_button`, tabs, nested panels и fullscreen pages.
- UI progress entity в Module SDK должен поддерживать общие layout-поля (`size`, размеры, `align`, `margin`, `padding`, `grid_column`, `grid_row`, `opacity`), компактный режим, скрытие видимых подписей и опциональные цветные фазы `progress_stages` вида `{ color, percent, name }`; compact progress с видимым title держит title слева в одну строку, в некомпактном режиме текущий процент и активная фаза отображаются в верхней meta-строке progress-а, а снизу остаются только подписи фаз.
- UI footer entity в Module SDK должен быть host-owned slot-ом модульного overlay: module-provided footer рендерится в левой части стандартного footer-а, а стандартная host-owned кнопка `Назад` по умолчанию отображается самой правой. Поле `hide_host_back_button: true` является явным opt-in для активной `footer`-сущности и скрывает стандартную кнопку только когда модуль полностью заменяет footer actions.
- Host-команда Module SDK `browse_window` должна быть универсальным host-owned способом открыть окно выбора папки, существующего файла или save target. Команда обязана поддерживать предсказуемые параметры `target`, `status_target`, `mode`, `title`, `start_dir`, `filters`, `default_name`, `default_extension`, `confirm_label`, `selected_status`, `overwrite_policy` и `can_create_directories`, одинаково работать в desktop/browser shell и записывать только выбранный путь/статус в UI state модуля без автоматического чтения, создания, перезаписи, CSV import/export или cloud-действий. Фильтры команды задаются basename/glob-масками через `filters[].patterns`, чтобы можно было выбрать как файлы по расширению (`*.csv`, `*.bat`), так и extensionless-файлы или семейства имён (`config`, `config.*`, `config*`).
- Module SDK должен поддерживать live-обновление host-owned UI state во время долгого `ui_action` через ABI callback `IntegrationHostEvent.event = "ui_values"` с payload `values`. Host применяет только явно названные module UI keys, не маппит внутренние события вроде `download_progress` на id конкретного модуля и отсекает поздние события после Stop/Close или устаревшего action-token.

## Теги наблюдений и cloud-выборок

- Тег нормализуется в upper-case, имеет длину `1..16`; допустимы только английские ASCII-буквы, цифры и `-_.`, любые пробельные символы запрещены, при этом обязательна минимум одна буква или цифра. Непустое невалидное значение отображается в поле ввода красным текстом и не может быть назначено.
- У приложения есть один текущий тег. Новое или повторное наблюдение получает текущий тег приложения, не теряя ранее накопленные локальные теги; смена тега не переписывает старые строки задним числом.
- Desktop и browser UI используют одинаковые typed entity names из shared `UiEntityKind`/модульного UI-контракта. В `Tracked apps` доступна квадратная кнопка тега того же размера и с той же окантовкой, что соседняя кнопка `X`, включая connector-managed строки без `X`: внутри используется отдельная SVG-иконка `T`, при назначенном теге меняется только заливка на голубую как у активного switch, без тега она остаётся тёмной. Пара `T`/`X` с уменьшенным внутренним промежутком занимает ровно ширину switch и выровнена с ним по левому и правому краям. Tooltip: `Тег - способ разделять данные одного приложения на регионы или группы`.
- Тег создаётся/выбирается локально только через строку приложения в панели `Отслеживаемые приложения`; назначение не требует cloud-авторизации и не создаёт tag namespace в облаке. Открытый modal не закрывается кликом по затемнённой области или после применения и закрывается только явной кнопкой `Закрыть`. Менеджер объединяет без дублей текущие теги приложений, теги локальных отображаемых observations и глобальный cloud-каталог. Верхняя строка предназначена только для substring-поиска и добавления отсутствующего валидного тега через `Добавить новый`/`Add new`; при пустом фильтре показываются все варианты. Текущее назначение приложения хранится и подсвечивается независимо от текста поиска. Клик по чипу выбирает тег, повторный клик снимает выбор; единая кнопка `Назначить`/`Assign` применяет выбранное состояние, в том числе отсутствие тега, поэтому отдельной кнопки снятия назначения нет. После применения поисковый фильтр сбрасывается и весь список возвращается. Строки, скрытые правилами `Игнорируемые адреса`, не поддерживают локальную историю тега: если тег снят со всех приложений и больше не встречается в отображаемом `Мониторинге`, он исчезает из локальных вариантов. Сначала выводятся теги автора, затем теги, одновременно принадлежащие автору и присутствующие в облаке, затем остальные cloud-теги; три источника имеют различимое, но согласованное с темой оформление. Удалить можно любой собственный тег. Перед удалением отдельный modal предлагает `Только на этом устройстве` или `На этом устройстве и в облаке`; локальное удаление снимает тег со всех приложений и observations, а cloud-вариант дополнительно удаляет только namespace/associations текущего аккаунта. Сами observations не удаляются. Повторное наблюдение endpoint после смены тега добавляет новую связь, не удаляя предыдущую. Cloud tag namespace и associations создаются только во время явной выгрузки tagged-строк мониторинга; прямые cloud API создания/переименования тега отсутствуют. Cloud export не содержит поиск, ввод или назначение тега и позволяет очистить все собственные локальные теги строк, выбранных в `Мониторинге` до открытия окна. В cloud export верхняя подпанель содержит только авторизацию и подпись автора; `Приватная выгрузка` и `Очистить теги` находятся в отдельной однострочной подпанели внутри `Публикации автора`, непосредственно над таблицей.
- Header панели `Monitoring` после switch `Публичные` и вертикального разделителя должен содержать сохраняемые switch `Теги` и `Соединение и Счет`, оба включённые по умолчанию. Во включённом состоянии первый отображает столбец тегов, второй отображает `Соединение` и `Сч.`; при отключении соответствующие столбцы визуально скрываются, а оставшиеся растягиваемые столбцы заполняют освободившееся пространство. Desktop и browser используют общие типизированные поля `app_settings`, сохраняемые как `ui.monitoring.show_tags` и `ui.monitoring.show_connection_count`.
- На аккаунт допускается не более `100` одновременно существующих cloud-тегов; локальные теги до выгрузки в этот лимит не входят. UI показывает использованный облачный лимит и поясняет освобождение тега после удаления либо истечения последних связанных cloud-строк.
- Одна логическая cloud-строка может содержать до `32` разных текстов тегов. Повторная загрузка существующей строки добавляет новые теги вместо замены старых.
- Таблица `Мониторинг` содержит колонку `Тег` сразу после `Приложение`; значение выводится однострочным read-only `path-field` с перемещением каретки по длинному значению, а ширина колонки рассчитана примерно на восемь символов тега. В таблице `Публикации автора` один и тот же app выводится отдельными строками для каждого точного набора локальных и уже опубликованных собственных тегов. Перед расчётом `Новые данные`/`New data` клиент авторизованно сопоставляет выбранные строки с D1 по `app_id + visibility + author + IP + port + protocol`: уже существующий endpoint с тем же собственным набором тегов не считается новым, а новый тег для существующего endpoint остаётся кандидатом выгрузки. Колонка `Тег` является крайней правой, имеет фиксированную ширину, достаточную для тега максимальной длины, кнопки `X` и служебного многоточия, и не показывает полос прокрутки. Каждый тег выводится отдельным read-only `path-field`, позволяющим перемещаться по значению; несколько тегов переносятся внутри ячейки. SVG-кнопка `X` удаляет только выбранный локальный тег у observations данной строки, тогда как общая кнопка `Очистить теги` удаляет все их локальные теги.
- Cloud import фильтрует каталог и строки по подстроке тега. Cloud-теги служат только server-side метаданными фильтрации и не импортируются в локальные наблюдения.
- CSV локальных строк заканчивается столбцом `tags` с `;`-разделёнными локальными тегами пользователя. CSV cloud staging также содержит последний столбец `tags`, но оставляет его пустым.

## Operational требования

- Все reusable entrypoints должны жить в `scripts/` или `tools/`.
- Все regression tests должны быть tracked в `tests/`.
- Централизованный test batch-runner должен жить в `tests/run.ps1` и поддерживать минимум suites `dev`, `regression` и `full`, чтобы project-owned verification path не требовал ручного набора отдельных `cargo test` команд.
- Секреты, локальные ключи и временные артефакты не должны попадать в git.
- Platform-specific monitoring backends и external integration host должны быть изолированы за capability-gated backend-слоем.
- Connector discovery не должен становиться Windows-only из-за текущего набора monitoring backend-ов; Windows, macOS и Linux discovery sources должны развиваться в одном connector module.
- Если `.app` manifest connector-managed приложения удалён из active connector set, приложение должно исчезнуть из `Tracked apps` после bootstrap через физическое удаление соответствующей строки `tracked_apps` из SQLite. Ручные приложения, добавленные пользователем через путь к executable и имеющие кнопку удаления, не должны удаляться этим cleanup. Исторические `observed_endpoints` при таком cleanup сохраняются без активной связи с приложением.
- Кроссплатформенный UI shell не должен зависеть от Windows-only кода для запуска.
- Каждая новая область проекта должна иметь чёткую границу ответственности и документированную точку входа.
- Portable-версия должна иметь рядом с `NetStitch.exe` все минимально необходимые runtime-файлы, нужные для локальной работы: native tool libraries в `libs/`, native integration module libraries/assets/locales/data в `integrations/`, папку `apps/` с редактируемыми коннекторами, папку `language/` с редактируемыми `.ini` локалями приложения, project-local `storage\` для SQLite/cache/export state и, для UDP/QUIC monitoring, WinDivert runtime-файлы `WinDivert.dll` и `WinDivert64.sys` в корне portable-папки из доверенного источника. Helper executables не являются portable runtime артефактами.
- После каждого project-owned compile action portable-папка `dist\NetStitch-win64-portable` должна обновляться свежими release-бинарниками и runtime-файлами.
- Подписывание Windows-артефактов должно использовать безопасный config contour: tracked только `config/signing.example.toml`, реальные значения и секреты только в ignored local contour.
- Project-owned `NetStitch.exe` и project-owned native libraries под `libs/` и `integrations/` должны быть основными кандидатами на подпись, если для конкретного формата доступен signing path; third-party runtime вроде `WinDivert.dll` и `WinDivert64.sys` не переподписывать NetStitch-сертификатом.
- Пока production-сертификат не настроен, допустим self-signed `test_certificate` для локальной разработки, проверки signing pipeline и test-signed release artifacts.
- `test_certificate` не является production trust и должен быть явно отражён в release/status отчёте, но не блокирует продвижение ветки `release` и создание release record.
- Все project-owned Windows `.exe`, которым доступна подпись, должны также иметь заполненный Windows Version Resource: `CompanyName`, `ProductName`, `FileDescription`, `InternalName`, `OriginalFilename`, `LegalCopyright`.
- Project-owned push contour должен поддерживать отдельный GitHub Deploy key для этого репозитория без зависимости от глобального ssh-agent. Процедура должна уметь: создать project-specific ключ, обновить `known_hosts` официальными GitHub host keys, настроить repo-local `core.sshCommand` с `IdentitiesOnly=yes` и иметь documented fallback через `ssh.github.com:443`, если обычный `github.com:22` недоступен.
- Git workflow проекта использует `development` для обычной разработки и `release` для релизной сборки/публикации. Ветка `main` не является частью текущего workflow: её не создавать, не пушить и не использовать как стабильную историю без отдельной прямой команды пользователя.
- Итоговый отчёт после каждого push должен быть стабильным machine-readable блоком: сразу после `Коммит: <short_sha>` всегда выводится строка `Tag: <tag_name>`; если git tag в этом push не создавался, не переносился и не был явно указан пользователем, строка остаётся пустой как `Tag: `.
- Версия проекта должна иметь формат `major.minor.patch.revision`: `major` означает принципиально новую архитектуру программы, `minor` - полноценную новую функцию, `patch` - изменение API, внутренних механизмов или небольшую доработку существующего функционала, `revision` - общий последний разряд, повышаемый на `+1` для каждой новой сборки или выпуска независимо от остальных разрядов. Windows и Linux portable-артефакты одного выпуска должны получать одинаковый `revision`.
- Каждое изменение версии проекта или сборочной ревизии должно иметь локально проверенный cross-platform install/build контур: Windows portable через `scripts\compile.ps1`, Linux portable и Linux `.deb` с тем же full-version, установка `.deb` в отдельный `NetStitch-Linux-Test` через package manager, проверка desktop launcher/runtime libraries и отсутствие задвоенных активных module roots в Linux.
- Verification path должен включать автоматическую high-confidence проверку tracked-файлов на секреты.
- Release asset packaging должен уметь собирать zip/tar portable-папки без включения `target`, runtime SQLite из `storage`, module runtime data из `integrations/<module>/data`, temp или local secret contours и должен проверять обязательные network runtime files: Windows `WinDivert.dll`, `WinDivert64.sys`, `libs\netstitch-tool\...\netstitch_tool.dll`, `libs\netstitch-watcher\...\netstitch_watcher.dll`; Linux `libs/netstitch-tool/.../libnetstitch_tool.so` и `libs/netstitch-watcher/.../libnetstitch_watcher.so`.
- Linux должен иметь отдельный installable Debian-package контур для ручной проверки на тестовом Linux/WSL: пакет строится из той же Linux portable staging-папки, содержит `NetStitch`, project-owned native `.so` runtime libraries и desktop launcher, объявляет системные GTK/WebKit/AppIndicator/xdo/OpenSSL/SQLite runtime-зависимости и устанавливается через package manager, чтобы тестировать именно install flow, а не запуск бинарника напрямую из `dist`. Системная установка кладёт read-only runtime в `/opt/netstitch`, а wrapper запускает приложение с user-writable `NETSTITCH__DATA_DIR`, `NETSTITCH__CONNECTORS_DIR` и `NETSTITCH__INTEGRATIONS_DIR` под `~/.local/share/netstitch`, чтобы основная SQLite БД, редактируемые connectors и module runtime data не писались в `/opt`.
- Push в ветку `release` должен запускать GitHub Actions workflow `Portable Release` для сборки Windows/Linux portable artifacts, Linux `.deb` package и публикации GitHub Release: базовая версия берётся из `[workspace.package].version`, а полный release version - из tracked `config\release-version.json`, обновлённого из локально протестированной portable-сборки. После успешной сборки workflow создаёт tag, GitHub Release и прикрепляет assets. Ручной `workflow_dispatch` с `publish_release=true` допустим только для явно подтверждённого повтора/аварийного запуска. Windows и Linux артефакты собираются с одинаковым `NETSTITCH__PACKAGE_REVISION`, а published archives/packages не должны содержать runtime SQLite, `integrations/<module>/data`, пользовательские connector manifests/cache или локальные temporary contours. Generated `dist\...\config\version-manifest.json` является результатом локального packaging и не коммитится; tracked `config\release-version.json` является источником версии для GitHub runner.
