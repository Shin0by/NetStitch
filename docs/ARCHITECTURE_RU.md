# Архитектура NetStitch

## Текущее состояние

Архитектура развивается как Rust workspace с разделением между кроссплатформенным desktop shell и platform-specific backend-возможностями: Windows advanced monitoring использует owner tables/WinDivert, Linux basic monitoring использует `/proc/net`.

## Базовые контуры

- `src/netstitch-shared` - общие модели, DTO, IPC-контракты, включая `cloud` DTO для Worker/client boundary
- `src/netstitch-cloud` - отдельный contour community cloud sync: client identity, quota, app-list/status refresh, verified-app upload policy helpers и request integrity helpers; модуль не должен выполнять cloud-запросы без явного action handler-а
- `src/netstitch-cloud-worker` - deployable Cloudflare Worker + D1 backend contour для community cloud sync; внешние Cloudflare resources именуются `netstitch-*`, внутренние D1 tables остаются короткими без префиксов
- Cloud auth boundary использует DTO из `netstitch-shared::cloud`: upload identity выдаётся только после Google OAuth/OIDC flow с Authorization Code + PKCE/state и server-side captcha/rate-limit policy. Worker хранит provider mapping, необратимые provider subject/email HMAC-значения через server-side secret `NETSTITCH_IDENTITY_PEPPER` и одноразовые OAuth/captcha states в D1, а desktop UI сохраняет только безопасные account metadata (`provider`, subject hash), local session/client state и display-only Google name/email в Windows DPAPI-защищённом storage-контуре. Google email/name могут быть полями текущего OAuth session response для отображения в UI, но Google email/name/raw subject, пользовательские пароли, Google access tokens, OAuth client secret и provider credentials в открытом виде в SQLite/логах/D1 обратимо не сохраняются.
- `src/netstitch-connectors` - модульные коннекторы известных приложений и discovery правил для `Tracked apps`
- `resources/connectors/apps` - tracked шаблоны runtime-коннекторов, которые portable packaging копирует в `apps/` рядом с exe
- `src/netstitch-core` - orchestration, SQLite storage, application services
- `integrations/host` - generic host для внешних интеграционных модулей
- `integrations/<module>/` - временный source/runtime contour внешних интеграций; модуль содержит manifest, `bin/`, `data/` и собственные crate/files до выноса в отдельный репозиторий
- `src/netstitch-watcher` - embedded watcher runtime/library для мониторинга, локального API и browser shell внутри основного процесса `NetStitch.exe`
- `src/netstitch-tool` - native network tool module (`rlib`/`cdylib`) для WHOIS/range cache, explicit domain lookup и network probes. Embedded watcher runtime вызывает библиотеку in-process. Домены мониторинга определяет watcher из HTTP Host, TCP TLS ClientHello SNI или QUIC Initial SNI.
- `src/netstitch-ui` - Dioxus Desktop приложение
- `src/netstitch-ui/src/app_watcher.rs` - UI-side adapter/facade для embedded watcher runtime API с опциональным mock-режимом для dev
- `config/` - tracked config schemas и безопасные примеры
- `storage/` - runtime state, logs и generated data вне git
- `resources/` - локальные assets, templates и fixtures
- `scripts/` - canonical project entrypoints
- `tools/` - reusable diagnostics и helper tooling
- `tests/` - tracked regression coverage

## Архитектурные принципы

- Shared/global contour документируется отдельно от прикладных модулей.
- До первого стабильного релиза архитектурные переименования делаются без obsolete/shim слоя: если контракт был назван неверно, старое имя удаляется, а source, docs, tests и scripts переходят на новое имя сразу. Это удерживает pre-release кодовую базу от накопления временных хвостов.
- Кроссплатформенный UI shell должен собираться как native executable сразу.
- Известные приложения не должны быть hardcoded presets внутри `netstitch-core`; они обнаруживаются через отдельные connector modules и добавляются disabled.
- Connector layer в runtime читает только внешние `.app` manifests из `apps/` рядом с exe/cwd или из `NETSTITCH__CONNECTORS_DIR`. Portable/installer поставляют shipped `apps/*.app`, но если этих файлов нет, приложение не создаёт и не восстанавливает их при запуске: active connector set остаётся пустым, кроме ручного добавления executable.
- Runtime-коннекторы являются declarative data manifests, а не исполняемыми плагинами: NetStitch читает только описанные локальные discovery rules и не загружает чужой код.
- Connector metadata включает `display_name` и `icon_key`; core сохраняет эти поля в `tracked_apps`, чтобы UI не выводил техническое имя процесса вместо пользовательского названия приложения.
- Core добавляет в snapshot `runtime_status`: счётчик connector-managed приложений, чьи `exe_path` существуют на текущей машине, и список сохранённых tracked apps с отсутствующим executable. Desktop и browser shell используют этот блок только как стартовую диагностику текущего запуска: один раз после первой загрузки непустого списка приложений сидят статус загрузки коннекторов и недоступные `Tracked apps`, не ведут повторное отслеживание app availability и не записывают эти event-строки в SQLite.
- Встроенный connector содержит embedded `.svg` bytes для UI; core при bootstrap пишет их в `apps\icons\<icon_key>.svg` и сохраняет `icon_path` в `tracked_apps`, чтобы UI/WebView показывал image asset без повторного извлечения из exe. Если пользователь положил `apps\icons\<icon_key>.svg` или `.png`, этот файл имеет приоритет.
- Manual path flow на Windows пытается извлечь shell/executable icon из выбранного файла и кэширует её как `apps\icons\manual_<path-hash>.png`; hash считается от нормализованного полного пути, поэтому одинаковые имена файлов из разных папок не конфликтуют.
- При bootstrap core повторно проверяет сохранённые active tracked apps с отсутствующей, битой или fallback-иконкой и пытается восстановить executable icon в `apps\icons`; это позволяет дозаполнить иконки для ранее добавленных manual-приложений без ручного удаления/добавления строки.
- Если executable icon извлечь нельзя, manual app получает cached `default.svg`, общий для fallback-состояния.
- `Tracked apps` сортируются в core: manual entries (`icon_key = manual`) идут сверху по `created_at_ms DESC, id DESC`, connector entries идут ниже по алфавиту display name. Connector-managed identity хранится как `connector_id`: если discovery находит новую versioned-папку того же продукта, core сохраняет одну строку продукта, переносит её на актуальный `exe_path`, сохраняет enabled/disabled состояние и удаляет stale-строки старых версий.
- `tracked_apps.exe_path` не является уникальным storage-ключом. Для connector-managed строк identity задаётся `connector_id`, поэтому пользовательские runtime-коннекторы могут создать несколько разных logical apps/профилей для одного executable path. Manual add flow при этом остаётся дедуплицированным по пути, чтобы повторный ручной выбор того же файла не создавал случайные дубли.
- При bootstrap core удаляет из SQLite connector-managed строки `tracked_apps`, чей `connector_id` больше не входит в активный набор manifests из внешних `apps/*.app`. Это именно удаление строки коннектора из БД, а не архивирование или скрытие; связанные `observed_endpoints` сохраняются как исторические строки с `tracked_app_id = 0` и исходным `process_name`, чтобы не терять monitoring data. Manual-приложения без `connector_id` не затрагиваются и остаются пользовательскими.
- Исключение приложения из `Tracked apps` выполняется через core/storage boundary как archive/untrack flow: приложение убирается из активного списка и дальнейшего мониторинга, но связанные `observed_endpoints`, app identity и verification evidence не удаляются. Observation lifecycle независим от membership приложения в активном списке: если monitoring data уже получены, только отдельное явное пользовательское действие над observations может удалить их. Snapshot/UI должны уметь показывать или экспортировать historical observations без активной строки в `Tracked apps`, не создавая orphan-ошибок.
- Core bootstrap не сидит manual-приложения по локальным путям. Новая SQLite БД может получить только найденные connector-managed приложения через connector discovery, и такие строки стартуют disabled; пользовательские manual-приложения создаются только явным добавлением пути.
- Known-app connector должен быть кроссплатформенным с первого появления: Windows local/App Paths/Store-MSIX, macOS `.app` bundle и Linux `.desktop`/Flatpak/Snap/PATH discovery описываются в одном модуле приложения.
- Runtime monitoring backend поддерживает Windows и базовый Linux `/proc/net` path; macOS остаётся отдельным backend-этапом.
- Platform-specific monitoring и внешние integration modules должны быть инкапсулированы за backend capability checks.
- Observation storage фиксирует не только endpoint-ключ, но и `connection_state` + счётчики `failed_hits/successful_hits`, чтобы UI мог отделять проблемные адреса для прицельного экспорта.
- CSV import/export является thin UI/control surface поверх core storage: desktop export сериализует выбранные строки `Monitoring` в табличный CSV с endpoint-колонками `application/ip/domain/port/protocol/connection/requests/first_seen/last_seen` и app identity/provenance полями, desktop import отправляет `MonitoringCsvImportRequestDto` в watcher route `/v1/observations/import-csv`, browser shell читает/пишет CSV через watcher-host filesystem routes `/v1/filesystem/read-text` и `/v1/filesystem/write-text`, а core выполняет накопительный upsert без очистки таблицы. Публичность IP является UI-фильтром через switch `Публичные`, но не отдельной monitoring/CSV колонкой и не отдельным счётчиком в header `Monitoring`. Для CSV import ключ уникальности намеренно глобальный по `remote_ip + remote_port + protocol`, а не по приложению, чтобы несколько CSV-файлов могли дополнять один monitoring dataset перед единым экспортом или передачей во внешний модуль.
- CSV import/export переносит идентификаторы приложения (`app_connector_id`, `cloud_app_id`) и доказательства происхождения (`app_signature_key`, subject, issuer). Core сохраняет эти поля на уровне observation и не заменяет импортированную подпись подписью текущего локального executable. Если импортированная подпись совпала с добавленным/найденным приложением, строка может считаться пригодной для verified upload; если приложение не установлено или подпись отличается, строка остаётся отправляемой в cloud как `CloudImportUntrusted` с исходной импортированной подписью.
- CSV не расширяется отдельной колонкой источника домена. Desktop export пишет в колонку `domain` только домен, который уже есть в snapshot как доказанный watcher-ом или доверенно импортированный ранее. Desktop import доверяет колонке `domain` как пользовательскому переносимому наблюдению и сохраняет её в endpoint-level cache с internal source `csv_import`.
- Удаление одной строки `Monitoring` начинается со стандартной square close-кнопки, но до core/API action обязательно проходит через modal-подтверждение. Подтверждение отправляет shared request `DeleteObservationRequest` в watcher route `/v1/observations/delete`, где core делает storage delete по `observed_endpoints.id`; этот action не удаляет tracked app и не трогает другие endpoint-строки.
- Windows monitoring backend состоит из TCP owner-table snapshot path, optional WinDivert FLOW stream path и optional WinDivert NETWORK sniff paths. FLOW path добавляет UDP/QUIC remote endpoints по `ProcessId`. Для любых выбранных процессов, где стандартные Windows таблицы показывают только локальный UDP socket, FLOW/packet contour является источником фактических remote endpoints после старта мониторинга; уже открытый socket тоже может быть учтён, если через него после старта проходит новый packet/event. Такие строки попадают в обычное observation storage как `remote_ip + remote_port + UDP`, а не остаются только внешней строкой игрового или app-лога. Реализация не хардкодит конкретные приложения, IP или диапазоны high ports: принадлежность определяется через process/PID/app ownership и endpoint tuple. UDP endpoint fallback открывает NETWORK sniff для исходящих UDP-пакетов с payload на любых remote ports, извлекает только IP/port tuple без сохранения payload и связывает packet с PID через Windows UDP owner table по локальному socket, включая wildcard socket вроде `0.0.0.0:<port>`. Отдельный domain NETWORK path тоже открывается только в sniff-режиме, не блокирует и не реинжектит пакеты, фильтрует исходящие TCP payload-пакеты и UDP/443 QUIC Initial, извлекает только HTTP `Host`, TLS ClientHello SNI или QUIC Initial SNI, не сохраняет payload и привязывает домен к строке наблюдения через `tracked_app_id + remote_ip + remote_port + protocol`, а не к одному IP. Чтобы не терять быстрые TLS/HTTP/QUIC handshakes, watcher держит найденные domain packets в короткой pending-очереди до PID-маппинга и использует недавние TCP owner/FLOW ключи ограниченное время.
- Watcher runtime больше не является отдельным operational CLI/helper процессом в portable runtime: monitoring/API/browser-shell логика встраивается в `NetStitch.exe` и живёт в lifecycle основного приложения.
- Project-owned network modules проектируются как native libraries, а не как скрытые helper-процессы. Embedded watcher runtime отвечает за мониторинг выбранных процессов, локальный API и browser shell. Native network tool module отвечает за сетевые lookup/probe/enrichment операции как linked/native library.
- Если headless/automation control surface понадобится снова, он должен быть новым documented app-owned entrypoint-ом в native-only runtime boundary.
- UI-side adapter должен развиваться как boundary к embedded watcher runtime без изменения экранов, моделей и user-facing strings. Выбор будущих automation/transport решений не должен превращать watcher/tool в скрытые сервисы.
- Header-фильтры `Monitoring` являются watcher-owned UI state, а не локальным состоянием отдельных оболочек. Desktop UI и browser shell отправляют единый `UiFiltersDto` в embedded watcher runtime (`/v1/filters`), runtime включает этот блок в каждый `snapshot`, а клиенты используют его как канонический источник правды для header controls и фильтрации таблицы. Switch `Публичные` является частью этого фильтра, но его последнее состояние сохраняется в SQLite `app_settings` (`ui.monitoring.public_ip`) и используется при старте watcher runtime.
- Browser shell обязан обновляться секционно: watcher публикует очередной `snapshot`, browser считает сигнатуры секций (`snapshotSectionSignatures`), строит delta (`snapshotSyncDelta`) и применяет только изменившиеся регионы через `applySnapshotSyncDelta`. Полный `render()` допустим только для действительно глобальных смен, например переключения локали.
- Обычные текстовые inputs в desktop и browser shell коммитят значение только по `Enter`, `change`/потере фокуса или явной кнопке действия. На `Enter` применяется стандартный pulse-класс. `oninput` для таких полей запрещён, чтобы фильтры и filesystem/path-поля не фризили UI во время набора.
- Footer `Message` является view над SQLite `system_events`: desktop и browser записывают footer-события как `component=ui`, `action_type=message`, `entity_type=footer`, `severity` и payload `{message}`. UI показывает последние 10, копирует последние 100, а core хранит не больше 9999 строк. Подряд идущие одинаковые события схлопываются увеличением `repeat_count`; если между ними появилась другая строка, повтор будет новым event row.
- Browser shell не использует native browser file input для project paths: общий server-side picker вызывает runtime routes `/v1/filesystem/browse`, `/v1/filesystem/read-text` и `/v1/filesystem/write-text`, поэтому выбор executable/profile/CSV относится к файловой системе машины, где запущен `NetStitch.exe`.
- Сетевые адреса для endpoint reachability probe не hardcode-ятся в native network tool module: caller обязан передать targets явно в library action `probe-endpoint` / `probe_endpoint`. Targets могут быть IPv4, bracketed IPv6 или доменами, например `udp://1.1.1.1:53`, `udp://[2606:4700:4700::1111]:53`, `tcp://example.com:443`. Операция проверяет доступность endpoint на порту, а не только DNS; без prefix порт `53` по умолчанию считается UDP, остальные порты - TCP. Для `tcp://<domain>:443` допускается HTTPS probe, чтобы footer DNS/network status опирался на реальный browser-safe path, а не только на raw socket connect. Desktop UI и browser shell читают editable `config\endpoint_probe_targets.txt` или overrides `NETSTITCH__ENDPOINT_PROBE_TARGETS` / `NETSTITCH__ENDPOINT_PROBE_TARGETS_FILE`, перечитывают targets при refresh и отправляют embedded watcher runtime в snapshot-запросе повторяющиеся `endpoint_probe_target` и `endpoint_probe_protocol`; runtime сериализует native tool calls и не выбирает список targets самостоятельно.
- Embedded watcher runtime сериализует linked native network tool calls: enrichment loop и endpoint probe loop используют общий runtime lock, поэтому внутри одного `NetStitch.exe` не выполняется несколько tool-задач одновременно.
- UI shell должен уметь продолжать жить в system tray независимо от состояния главного окна.
- UI shell должен иметь неблокирующий cold-start path: первый snapshot создаётся локально, а bootstrap embedded watcher runtime и чтение SQLite выполняются после первого paint окна.
- UI-side watcher adapter не должен выполнять blocking snapshot refresh из render/snapshot path; live snapshot загружается фоновым job и применяется в UI после готовности результата.
- Когда открыт модульный overlay, desktop shell приостанавливает фоновый snapshot refresh и window-lifecycle polling. В обработчике native window events нельзя на каждом move/drag событии синхронно опрашивать состояние окна; hide-on-minimize проверяется только на resize/minimize-контуре, чтобы native window-drag loop и modal repaint не конкурировали с периодическим re-render и не вызывали фризы при перетаскивании окна за заголовок.
- Watcher lifecycle принадлежит основному процессу `NetStitch.exe`: при закрытии UI останавливает embedded runtime и освобождает native resources; owned helper child process отсутствует.
- Bulk `Enable all` в desktop UI идёт через generic watcher endpoint `/v1/settings` и является overlay-настройкой `ui.enable_all_overlay` в SQLite `app_settings`, а не массовым update `tracked_apps.enabled`; monitoring backend использует effective tracked apps, где overlay временно делает все приложения enabled без потери индивидуальных флагов.
- UI shell должен разделять user-facing text и технические UI-сущности; стабильные ids/data attributes живут в `src/netstitch-ui/src/ui_entities.rs` и используются для тестов/automation вместо текста.
- Header является общей UI-сущностью для всех внутренних панелей и overlay-окон проекта; единственное исключение из этого контракта - глобальный header главного окна приложения. Контракт внутреннего header: слева заголовок (`h1/h2` или эквивалент), рядом опциональная круглая help-сущность `?`, справа опциональный status/meta label. Другие элементы во внутреннем header запрещены: описательный help-текст, предупреждения, action-кнопки, form controls и длинные пояснения должны находиться в body или footer соответствующей сущности. Header не должен расти из-за локализации длинного текста; длинные объяснения всегда выносятся в tooltip `?` или body.
- `Tracked apps` является canonical UI reference для desktop/browser shell: базовые panel/header/input-box/button/switch/list-row стили в `src/netstitch-ui/src/theme.rs` и embedded browser CSS должны наследовать его плоскую Workbench-палитру, compact `5px` spacing, скругление `3px`, tooltip contract и stable entity/action selectors. Все panel headers используют одинаковую высоту, padding, h2 typography и `title-with-help` структуру; глобальное пояснение панели живёт в help `?`, а не в отдельной строке body/header. Header-статусы и счётчики не используют badge/chip/pill surface внутри panel header, а рендерятся как лёгкий `panel-header-meta` текст. Новые UI-сущности того же типа нельзя проектировать отдельным стилевым островом без явного решения.
- `path-field` является обязательной shared UI-сущностью для отображения filesystem/location значений в desktop и browser shell. Компонент реализуется как single-line input-like control с внутренней горизонтальной прокруткой и без переноса текста; parent panel/list не должен получать горизонтальный scroll из-за длинного пути. Для labelled/path значений с модификатором content-width поле сначала стремится к ширине текста, но не шире доступного контейнера; если значение не помещается, показывается ellipsis, а при focus включается внутренняя горизонтальная прокрутка без ellipsis. Read-only path-field остаётся focusable/selectable/copy-friendly, а clickable path-field добавляет pointer cursor, tooltip и собственный click handler без всплытия события в parent row. Новые места вывода путей не должны дублировать path CSS вручную и не должны использовать обычные `p/span` для длинных путей.
- Цвет text-like UI-сущностей определяется смыслом значения, а не типом control. Если значение уже имеет видимый ярлык или колонку (`Domain`, `Integration folder`, `Provider`, `Primary path`, `Export path` и т.п.), оно рендерится основным текстовым цветом `var(--color-text)` / `var(--text)`, даже если визуально использует shared `path-field` или `value`-сущность. Muted-цвет разрешён только для второстепенных данных без собственного ярлыка, например для пути внутри row `Tracked apps`, placeholder/help/diagnostic copy и других явно auxiliary-полей. Новые entity-классы значений не должны автоматически наследовать muted-цвет от `path-field`, если это labelled value.
- Все panel/modal/overlay header-ы в desktop/browser shell имеют строгий состав: заголовок, опциональная круглая подсказка `?` и опциональный статус/мета-лейбл справа. Описательный help-текст, предупреждения и длинные пояснения не размещаются в header.
- Все overlay-окна desktop/browser shell состоят из трёх стабильных блоков: `modal__header`, `modal__body` и `modal__footer`. Header и footer используют одинаковый panel-block стиль: тот же фон, border-разделитель и `6px 8px` padding; body может отличаться по содержимому и внутренним layout-правилам. Кнопки со смыслом `принять/отмена` или близким к ним всегда размещаются в `modal__footer`, а не в body. Все modal-подтверждения удаления в desktop shell проходят через общий компонент `ConfirmDeleteDialog`: сменяемые `title/help/body lines`, общий `modal__footer`, стабильные action/id и одинаковая геометрия кнопок; help-текст confirm-overlay выводится в `modal__body` над деталями действия. Browser shell использует тот же визуальный контракт и общий helper построения body-строк, чтобы удаления приложений/наблюдений/ignore-правил не расходились по поведению.
- Overlay `Информация` является справочным UI-contour без backend actions: header не содержит `?`, footer содержит только закрытие, а body состоит из двух panel-секций с собственными header/body/footer. Верхняя секция `О программе` фиксируется по контенту и использует embedded branding image `resources/branding/images/NetStitch.png`; нижняя секция `Информация` занимает оставшееся пространство и скроллит только свой body с группами пояснений.
- Tooltip является отдельной UI-сущностью, а не случайным native `title`: если используется `data-tooltip`, native `title` не задаётся, чтобы не было задвоения подсказок. Реализация должна иметь единый desktop/browser стиль, появляться рядом с контролом через общий floating tooltip-layer, рендериться поверх card/list/scroll-контейнеров, иметь safe alignment или viewport-aware placement у краёв окна и не зависеть от `overflow` родительской панели. Любой новый tooltip contract должен сразу учитывать desktop и browser shell, чтобы подсказка не обрезалась `Tracked apps`, footer, scroll-subpanel или границами окна и не была без причины прижата к краю окна.
- Основной desktop/browser layout фиксирует алгоритм панелей, а не перестраивает структуру при resize: глобальный header содержит фильтр наблюдений, поиск и кнопки управления мониторингом; справа в header находится вертикальный стек switch-ов `Расшир. монитор.` над `Web сервер`, прижатый к правому краю. Рабочая область всегда делится на две равные по ширине колонки. Левая колонка занята `Tracked apps`, правая сверху вниз - `Модули` и `Ignored addresses`. `Модули` берут только фиксированную по контенту высоту и показывают module action buttons, `Ignored addresses` берёт высоту только от числа своих видимых строк; обе правые панели используют фиксированные промежутки между собой и не добавляют внутренние placeholder-ы для выравнивания. После вычисления высоты правого верхнего стека `Tracked apps` растягивается до той же нижней линии; внутри него сначала резервируется целое число полных строк приложений в scroll-списке, а оставшийся вертикальный остаток между строкой пути и bulk-row добирается отдельным spacer-элементом под путём. Все scroll-list подпанели резервируют правый scrollbar-gutter даже без видимого scrollbar, чтобы строки не меняли ширину и не прилипали к правому краю при изменении количества строк. Ниже верхнего стека вся оставшаяся высота окна отводится full-width панели `Monitoring`, у которой сама панель и её `table-wrap` заполняют доступное пространство, но не выталкивают главное окно в глобальный scroll. Отдельная панель `Status and errors` исключена, потому что runtime status/error строки живут в footer `Message`.
- Footer получает отдельные UI-сущности статуса embedded monitoring runtime, статуса доступности native network tool library, статуса browser web server, статуса endpoint reachability, runtime message panel и language dropdown: live adapter выставляет техническую готовность runtime, чтобы зелёный/красный индикатор отражал именно доступность embedded watcher API, watcher snapshot выставляет `runtime_status.tool_available`, чтобы отдельный индикатор отражал linked network tool capability, web server indicator читает persisted setting `web.localhost_enabled`, а клик по нему копирует browser URL в clipboard и пишет событие в footer message panel. DNS/network indicator читает `runtime_status.endpoint_probe`: зелёный, если найден первый успешный endpoint target, красный если успешных target нет; tooltip показывает первый успешный target и полный список endpoint probe addresses со статусами `True/False/Checking`. Проверка DNS выполняется в embedded runtime как кэшируемая фоновая диагностика, продолжает собирать статистику по остальным target после первого успеха, но для выбора рабочего адреса использует первый успешный по порядку. Default embedded-runtime bind/base URL использует local-machine IP, desktop вычисляет такой URL локально, browser shell получает его через `/v1/web-url`; если локальный IP определить нельзя, footer пишет fallback-событие и использует localhost URL. Footer-контейнеры не имеют собственного фона/рамки, разделяются только вертикальными separator-линиями; счётчики строк `Monitoring` живут в header панели `Monitoring`, а не в footer. Message panel занимает свободное пространство между web server и language, выводит последние сообщения из SQLite `system_events`: в UI показываются последние 10, copy-history копирует последние 100, tooltip остаётся viewport-safe и показывает последние 6 строк без переноса по ширине. Все footer-сообщения пишутся в `system_events` с системными `component/action_type/severity/entity/payload`, цвет берётся из `severity`, а подряд идущие одинаковые сообщения схлопываются увеличением `repeat_count`; если между ними было другое сообщение, создаётся новая строка. Таблица ротируется до 9999 строк. При старте в лог записываются build/current/app, watcher, tool, web server, DNS, затем connector/module diagnostics. События включения/отключения web server должны содержать URL в той же строке; готовность или ошибка embedded runtime, загрузка коннекторов и недоступность сохранённого приложения тоже являются footer events. Текст `The UI will retry automatically` и `Integration note: No export yet` не являются footer-сообщениями. Language остаётся справа и сохраняет стандартный `input-box` фон/border; language dropdown является кастомной UI-сущностью с separator-линиями между option-строками, чтобы список был привязан к контролу, не менял геометрию footer при открытии и оставался выше overlay backdrop.
- Cold-start snapshot не должен сидить footer error `Watcher endpoint not reachable yet`; ошибки embedded watcher API допустимы только после реальной неуспешной попытки runtime operation.
- UI shell должен развиваться с language-boundary: локали поставляются внешними `.ini` файлами в `language/` рядом с exe, language select в footer строится из `[language].name` и locale-code этих файлов, выбранная локаль сохраняется в SQLite `app_settings` под ключом `ui.language`, падает на английский fallback `en-en` при отсутствующих ключах, а новые user-facing строки нельзя добавлять только в одну shipped локаль.
- Core storage содержит расширяемую таблицу `app_settings(setting_key, setting_value, updated_at_ms)` для project-local пользовательских параметров; сейчас в этом контуре уже живут `ui.language`, `ui.enable_all_overlay`, `ui.remember_window_placement`, `ui.hide_when_minimized`, `ui.window_x`, `ui.window_y`, `ui.window_width`, `ui.window_height`, `ui.window_hidden`, `ui.modules.order` и `web.localhost_enabled`, поэтому новые мелкие core/UI runtime опции должны добавляться туда же без отдельной таблицы на каждую настройку. Внешние интеграционные модули не хранят свои настройки и данные в основной SQLite БД: каждый модуль получает собственный portable storage внутри `integrations/<module>/data/`, а его рабочая SQLite БД называется `module.sqlite3`.
- Core storage содержит таблицу `ignored_addresses(id, address_pattern, created_at_ms)` для UI/runtime ignore-list. Bootstrap сидит loopback-правила `127.0.0.0/8` и `::1/128`, а при каждом schema/bootstrap проходе idempotent добавляет обнаруженные локальные IP текущей машины как точные CIDR-правила `/32` или `/128`; обнаружение использует ordered route-probe fallback по 8 IPv4 и 8 IPv6 DNS/anycast targets с `10s` timeout на попытку, а в список попадает только IP, который ОС вернула как локальный source address и который не относится к special/transition ranges вроде Teredo `2001:0::/32` или 6to4 `2002::/16`. UI фильтрует отображение и batch-confirm только по этому списку, без отдельного localhost-флага и без удаления observed endpoints из SQLite. Desktop/browser панель `Ignored addresses` отображает этот список как compact list-подпанель по контракту `Tracked apps`: row на один адрес, фиксированная IP-колонка `230px` через shared `path-field` с основным светлым текстом и внутренней горизонтальной прокруткой для IPv6/CIDR, tooltip `?`, domain-field и стандартная square delete-кнопка справа; list-контейнер использует тот же scroll/padding/border contract, что `Tracked apps`, а высота рассчитывается ровно на семь tuned-строк от старой compact-высоты `30px` с учётом gap, padding и border. Label внутри body не дублируется, потому что название живёт в header панели, а header `?` этой панели может иметь локальную позиционную поправку `-2px`. Удаление правила идёт через стабильный modal-confirm flow, а localhost/local-IP правила получают поясняющий текст перед подтверждением.
- Runtime snapshot содержит `runtime_status.domain_capture` с диагностикой payload-level доменного контура: стартовал ли WinDivert packet backend, сколько NETWORK-пакетов увидено, сколько payload-пакетов разобрано, сколько HTTP Host/TLS SNI/QUIC SNI доменов найдено, сколько привязано к tracked app, сколько ожидает owner-match и сколько отброшено из-за отсутствия owner/process/tracked app. Эта диагностика не выводится постоянной строкой в footer, чтобы не шуметь в обычной работе; footer пишет только событие включения/отключения определения доменов и одноразовую ошибку backend-а, например требование запустить NetStitch от имени администратора.
- Runtime snapshot содержит `runtime_status.flow_capture` для WinDivert FLOW/packet endpoint capture. Он нужен для полевой диагностики случаев, когда внешний лог выбранного приложения показывает remote UDP endpoint, Windows TCP tables и NetStitch table показывают только сопутствующие TCP endpoints, а UDP socket приложения виден только как локальный listener/socket. Диагностика показывает, стартовали ли FLOW и packet backend-ы, пришли ли UDP events вообще, были ли они отброшены до/после PID matching, и почему endpoint не попал в `Monitoring`.
- IP enrichment является отдельным native tool contour, а не частью hot monitoring path. Embedded watcher runtime асинхронно вызывает linked native network tool library короткими one-shot задачами, если setting `ip_enrichment.enabled` не выключен. Tool пишет WHOIS ownership ranges в `ip_whois_ranges` и throttle/status metadata в `ip_domain_cache`; домены monitoring rows хранит `endpoint_domain_cache` вместе с `domain_source` (`http_host`, `tls_sni` или trusted `csv_import`) и ключом строки наблюдения `tracked_app_id + remote_ip + remote_port + protocol`, чтобы shared CDN IP не смешивали разные домены. `netstitch-core` при сборке snapshot присоединяет кешированные `domain/source/owner/range` к `observed_endpoints`, а `ignored_addresses` получают только IP-level owner/range metadata. Snapshot/API/UI никогда не выполняют DNS/WHOIS синхронно, поэтому зависший или неудачный lookup не блокирует мониторинг и окно. WHOIS range cache ограничен `1000` строками и ротируется по `updated_at_ms DESC, id DESC`; если диапазон уже есть в кеше, принадлежность IP определяется локально без нового WHOIS-запроса.
- Native network tool module поставляется как библиотека. Его library ABI должен иметь безопасный default contour: все DNS/WHOIS/probe операции запускаются только явным runtime action-ом, получают targets от caller-а, возвращают structured result/error и не стартуют самопроизвольно при загрузке библиотеки.
- Embedded watcher runtime может отдавать browser shell на корне уникального порта `https://<local-ip>:46473/`, но только если core setting `web.localhost_enabled` включён; `/web` и app-name path не публикуются. `NETSTITCH__WEB_UI=1` используется как стартовый default, пока persisted-настройка отсутствует. Default bind address выбирается как `<local-ip>:46473` и падает на `127.0.0.1:46473`, если IP определить нельзя; явный app-owned bind override должен оставаться настройкой основного процесса. `/v1/web-url` добавляет к browser URL `#web_key=<derived-key>` fragment; browser JS отправляет ключ POST-запросом в `/v1/web-auth`, получает HttpOnly SameSite cookie и удаляет fragment из адресной строки. Middleware проверяет same-origin/CSRF before API actions, требует web-auth cookie для browser API и пишет audit-события remote browser actions. HTTPS certificate/key создаются app-owned в portable `storage/` как self-signed pair. Страница дублирует основные desktop-панели поверх уже существующего local API, поддерживает выбор языка через `/v1/languages` + `ui.language` и не использует `file://` для иконок: app icons запрашиваются через route по `tracked_app_id`, а кнопочные SVG-иконки отдаются как встроенные watcher assets.
- Tray flow не должен ломать runtime при пустом или неточном пути внешней интеграции; корректный root должен определяться отдельным integration-слоем.
- Desktop tray flow является тонким control-surface поверх уже существующих UI/runtime actions: `Показать/Скрыть окно`, `Скрывать в свёрнутое`, `Web сервер`, `Запоминать положение`, `Начать/Остановить сканирование` и `Выход` не создают второго runtime-контура, а используют те же window/snapshot/settings механизмы, что и основной UI. `Скрывать в свёрнутое` меняет persisted setting `ui.hide_when_minimized`, `Web сервер` меняет `web.localhost_enabled`, а `Запоминать положение` включает сохранение/восстановление геометрии окна и hidden-state через `ui.window_*`/`ui.window_hidden`; cold start всегда показывает главное окно видимым, даже если прошлое завершение сохранило скрытое состояние.
- Внешний модуль описывается manifest-файлом `integrations/<module>/module.json` со schema/version/id/display/icon/transport и платформенными путями `library_paths` к native shared library entrypoint: Windows использует `.dll`, Linux - `.so`, macOS - `.dylib`, а ABI остаётся общим C/JSON контрактом. Расширение Module API не меняет C ABI и не вводит отдельный Windows/Linux контракт: новые возможности передаются JSON action/payload/commands через тот же entrypoint. Host выбирает путь по ключам `<os>-<arch>`, `<os>`, затем `default` и загружает библиотеку через native dynamic loader. Пока модуль живёт в текущем репозитории, его source находится внутри `integrations/<module>/crates/` или эквивалентного локального контура; runtime binary кладётся в `integrations/<module>/bin/`, а модульная БД `module.sqlite3`, скачанные внешние приложения, cache и generated files - в `integrations/<module>/data/`. Имена модулей `core` и `system` зарезервированы регистронезависимо, чтобы не конфликтовать с source системного лога.
- Core/watcher/UI не hardcode-ят конкретные структуры файлов внешних продуктов. Они передают модулю локальные рабочие данные NetStitch через ABI/API: monitoring rows, выбранные rows, адреса, домены, диапазоны, порты, connection metrics и локальные подписи приложений. Модули не получают cloud credentials, cloud account state, токены, пользовательские секреты или прямой доступ к основной SQLite БД.
- Integration host предоставляет generic UI entity DTO: surfaces, panels, headers, footers, subpanels, grids, tables, rows, cells, value labels, status labels, path fields, buttons, icon actions, inputs, progress bars, help text, standard dialogs и action descriptors. Модуль описывает UI как схему и state patch, а desktop/browser shell рендерят это теми же сущностями, что и основное окно. Текстовые `input`/`textarea` сущности включают встроенный clear-`X` только через явный `clear_button: true`, а Enter-применение - через `commit_on_enter: true`; host renderer синхронизирует disabled-состояние кнопки локально в UI и держит черновой ввод в renderer state, без записи module/app state на каждый символ. Табличная `table` entity поддерживает `table_columns` для настройки конкретных TSV-столбцов, включая `text_field: true` для стандартного ограничивающего path-field контейнера внутри ячеек. Progress entity поддерживает общие layout-поля, compact/hide-label режимы и `progress_stages` с фазами `{ color, percent, name }`; desktop/browser renderer-ы одинаково показывают цветные сегменты и текущую фазу. Runtime-подписки на host events вроде `filters.*`, `monitoring.*` и `tracked_apps.*` включаются только host-командой `start_background` из явного пользовательского `ui_action`; такие события идут в модуль через тот же native C/JSON entrypoint и используются для обновления module-owned state/UI, но не означают autostart. Dynamic updates идут через module actions, host events и snapshot refresh, поэтому данные в overlay могут обновляться без перезапуска окна.
- Desktop/browser renderer-ы применяют единый слой defaults к UI-сущностям модулей перед построением DOM/Dioxus: `size = "stretch"`, `width = "100%"`, `min_width = "0"`, `opacity = "100%"`, `align = "left"` для любой сущности, `height = "auto"`, `min_height = "0"`, `scroll = "off"` для panel-like контейнеров и адаптивные `columns/gap` для `grid`, если manifest не задал поля явно. `footer`-сущности извлекаются из body-схемы и рендерятся в стандартном `modal__footer` как левая slot-часть. Host-owned кнопка `Назад` всегда добавляется справа и остаётся самым правым элементом footer-а; скрытие возможно только через явный флаг активной `footer`-сущности `hide_host_back_button = true`.
- Module UI actions идут через `/v1/integrations/ui-action`. Host передаёт модулю безопасный `IntegrationModuleHostContextDto`: версию приложения, язык, состояние мониторинга, текущие фильтры, счётчики таблиц, id выбранных/отображённых строк, выбранные monitoring rows и счётчики tracked apps. Ответ модуля может вернуть сообщение, severity, refresh flag и whitelist-команды host-а: изменение фильтров, запуск/остановку мониторинга, добавление/удаление/enable/disable tracked apps, операции над monitoring rows, `start_background`/`stop_background`, `log_event` и `show_dialog`. Фоновые module-owned задачи не стартуют при запуске NetStitch или обнаружении модуля; их старт всегда идёт через явное действие пользователя, включая header/action первого уровня после открытия overlay. `show_dialog` использует стандартный модульный диалог `OK` или `OK+Cancel` с `buttons = "ok"` / `buttons = "ok_cancel"`, title/icon модуля и логирует результат. Severity фиксируется системными уровнями `info`, `success`, `warning`, `error`. Cloud upload/download и CSV import/export не автоматизируются модулями.
- Панель главного окна `Модули` показывает только доступные module action buttons, сохраняет пользовательский порядок в `ui.modules.order` и при startup пишет в footer статус подключения каждого модуля или ошибку с причиной. Нажатие на кнопку открывает overlay первого уровня для выбранного модуля; дальше модульная схема может показывать provider/download/export/configuration controls, но визуальный контракт остаётся shared desktop/browser contract NetStitch.
- Скачивание внешних продуктов выполняется только explicit API/UI action модуля. Host не знает внешних URL и не загружает их сам; модуль обязан выполнять path traversal checks, хранить скачанный content в своём `data/` и возвращать progress через универсальный `IntegrationDownloadProgressDto`.
- Profile/export-like flows внешних модулей должны быть no-write на preview/analyze, иметь explicit apply/backup/revert действия, отклонять absolute/outside-root/path traversal значения и не менять monitoring flags вроде `is_confirmed`/`is_exported` без отдельного core action. Ошибки модульного export/setup/download не должны валить monitoring, watcher API или UI shell.
- Новые модули должны иметь явные границы ответственности.
- Community cloud upload группирует данные по `cloud_app_id`, trust/source-kind и стабильному ключу identity приложения. Один upload batch принимает от 1 до 65535 строк, а `limit_count = 0` в quota означает безлимитный режим операций upload/download. Verified-группа требует локально собранный stable app identity key; серверный список разрешённых издателей не используется. Ключ хеширует валидный Authenticode leaf SPKI, если он есть, и стабильные VersionInfo поля `CompanyName`/`ProductName`, нормализованные в нижний регистр. Версии, путь и имя exe не участвуют. Worker пополняет D1 `app_catalog` из authenticated upload payload и отклоняет только явно `blocked` app ids. Imported/untrusted-группа сохраняет source kind `CloudImportUntrusted` и исходную imported signature без подмены текущим локальным приложением. D1 хранит `publisher_key` как часть primary key observations/author rows для provenance и защиты от конфликтов записи, но публичный cloud catalog/download схлопывает строки тем же логическим ключом, что Monitoring/CSV: `app_id + IP + port + protocol`. Приватный/author-scoped срез является отдельным namespace и может учитывать тот же endpoint отдельно для владельца.
- Cloud upload/download используют `operation_id` как технический id пользовательской операции. Worker хранит его в `client_quota_operations` на время текущего quota window и списывает quota только при первом batch/page этой операции; следующие страницы download или batch-запросы upload с тем же id не считаются отдельными лимитируемыми операциями. Старые клиенты без `operation_id` остаются совместимыми через fallback: download списывается на `offset = 0`, upload списывается на каждый запрос.
- Community cloud author model разделяет auth identity и public author identity. Google OAuth provider subject/client key остаются внутренней авторизацией, а публичная `author_signature` выбирается при upload через обязательное UI-поле `Никнейм`. Ник не заполняется из Google, не может быть пустым, принимает только ASCII whitelist `A-Z`, `a-z`, `0-9`, `!.@#$%^&*()_+=-~` и ограничен `32` символами. Worker хранит display value и нормализованный `author_signature_norm = lower_ascii(author_signature)`, а уникальность проверяет по normalized value, поэтому разные регистры одного написания не создают разные ники. Отдельный reserved-list отклоняет только явно заданные служебные ники в любых регистрах. UI проверяет доступность ника отдельным Worker endpoint с debounce `1.5s` и отображает compact status underlay без попытки upload. Ник привязан к конкретной Google identity через необратимый provider subject hash/HMAC с server-side secret pepper; разные Google accounts являются разными authors и могут иметь разные ники. Cloud observations/submissions хранят стабильный `author_user_id`/provider-subject-hash reference, а не денормализованную копию ника; текущий ник подтягивается через join с author profile/catalog при выдаче и поиске. Поэтому смена ника владельцем на свободный валидный normalized value автоматически переводит уже опубликованные данные на нового `Автора` без переписывания endpoint rows. Email, display name и raw provider subject не являются storage/search/display полями. В cloud download/search этот public author signature отображается как `Автор`. Поиск cloud catalog должен поддерживать query по имени приложения и source/public author signature; author-scoped download для текущего пользователя строится server-side из session, а не из произвольной строки клиента. Endpoint `GET /v1/users/me/apps` возвращает текущий `author_signature` текущего автора вместе с его приложениями; UI использует это значение для кнопки `Мои публикации`, заполнения author-фильтра и колонки `Авторы`, а локально сохранённый ник является только fallback.
- Cloud download UI должен иметь локальную таблицу staging-строк, независимую от текущей таблицы `Monitoring`: выбор всех/ничего/отдельных строк, сортировка/фильтр по тем же базовым endpoint-полям, cloud-only колонку `Прив.` / `Private` со значениями `true`/`false` для признака приватного источника и действия `Добавить в мониторинг` и `Экспорт CSV`. Эти действия активны только при явном выборе staging-строк; пустой выбор не означает `все строки`. Добавление в мониторинг использует тот же core import/upsert path, что CSV import, но передаёт source `cloud_download`, сохраняет только cloud provenance/trust markers, относящиеся к приложению/endpoint, и возвращает requested/imported/skipped counts. CSV export использует общий CSV serializer, чтобы выбранные cloud-строки можно было сохранить в файл без промежуточной записи в monitoring storage. Progress bar cloud upload/download строится сегментами по 500 записей: например 1600 строк отображаются четырьмя шагами. Ни monitoring storage, ни CSV serializer не должны принимать или писать public author signature, email, provider subject, user id, client id или cloud privacy marker; privacy marker существует только в cloud staging UI.
- Browser shell реализует cloud import/export как web-shell над native watcher: UI JavaScript использует только local-origin `/v1/cloud/*` routes, включая `/v1/cloud/upload`, а внешний Worker/Cloudflare URL известен и используется только watcher-side proxy/client code. Это сохраняет единый trust boundary: веб-страница повторяет desktop controls и таблицы, но не получает самостоятельный внешний API client.
- Cloud search filters используют тот же UX contract, что header-фильтры `Monitoring`, но являются cloud-owned state, а не watcher-owned `UiFiltersDto`: верхний app catalog search имеет app/company/author text-фильтры и compact dropdown `Private`, которые обновляют только локальный ввод во время набора и ходят в Worker только после явного `Enter` или смены namespace; поле в момент применения делает одну короткую pulse-анимацию. Dropdown `Private` выбирает cloud download namespace в порядке `Все`, `Общие`, `Приватные`, влияет на колонку `Строк` в списке приложений и downstream download; `Все` добавляет приватные строки только для текущей авторизованной сессии. Нижняя staging-таблица после выбора app загружается по `app_id`, а IP/domain/port/protocol фильтруются локально по уже полученным строкам. Author заменяет local status и является публичным ником/подписью автора cloud-публикации, а не trust/status enum. App autocomplete возвращает/показывает до `5` первых вариантов без прокрутки и scrollable список остальных, но downstream download всегда использует выбранный `app_id`.
- Основной расширяемый контракт app-коннекторов - внешние `.app` манифесты в `apps/` или в `NETSTITCH__CONNECTORS_DIR`. Core предоставляет только общие discovery strategies (`app_paths`, `known_path`, `fixed_path`, `root_paths`, `registry_strings`, `store_msix`, `macos_bundle`, `linux_desktop`, `linux_path`) и не должен получать ветки кода под конкретные community-приложения. Rust known-app modules внутри `src/netstitch-connectors/src/modules` являются source/dev-контуром для shipped manifests и тестов, но не используются как runtime fallback, если внешних `.app` файлов нет.
- Identity приложения, найденного connector-ом, принадлежит connector manifest, а не текущему executable/process name. Поля `display_name`, `icon_key` и connector icon path должны восстанавливаться из connector discovery при bootstrap/seed, если существующая строка по тому же `exe_path` была ошибочно manualized или получила process-derived имя. Toggle enabled/disabled всегда меняет только `tracked_apps.enabled` по id и не должен вызывать add-app/upsert flow, чтобы `WhatsApp` не превращался в `WhatsApp.Root`, connector-иконка не заменялась manual-иконкой, кнопка удаления не появлялась у connector row и порядок списка не менялся из-за смены `icon_key`.
- `ConnectorManifest` должен содержать платформенные process aliases и discovery sources, чтобы UI/watcher могли разделять product identity, найденный executable path и runtime process matching.
- Discovery layer должен вести к reusable tooling без поиска по всему репозиторию.
- Core runtime не должен зависеть от сети там, где зависимость можно убрать локальными данными или кешем.
- Версия проекта имеет единый формат `major.minor.patch.revision`. `major` фиксирует архитектурный разрыв, `minor` - полноценную новую функцию, `patch` - изменение API, внутренних механизмов или небольшую доработку существующего функционала, а `revision` является общим счётчиком сборок/выпусков и повышается на `+1` при каждой новой сборке/публикации. Versioning layer должен выдавать одинаковый full-version для `NetStitch.exe` и project-owned native libraries в рамках одного portable-выпуска.
- Portable staging является минимальным пользовательским runtime-пакетом: release `NetStitch.exe` с embedded watcher runtime, native tool libraries under `libs/`, native integration module libraries/assets/data under `integrations/`, editable `apps/`, editable `language/`, portable `storage\` и опциональные WinDivert runtime-файлы `WinDivert.dll`/`WinDivert64.sys` в корне portable-папки из локального trusted path. Helper executable lifecycle в portable-пакет не входит.
- Linux installable packaging строится поверх Linux portable staging, но устанавливает read-only runtime в системный контур `/opt/netstitch`, wrapper `/usr/bin/netstitch` и desktop launcher `/usr/share/applications/netstitch.desktop`; системные GTK/WebKit/AppIndicator/xdo/OpenSSL/SQLite библиотеки остаются package-manager зависимостями, а project-owned runtime libraries поставляются внутри `/opt/netstitch/libs`. Wrapper не пишет runtime state в `/opt`: он создаёт `~/.local/share/netstitch`, копирует туда shipped connector manifests и integrations без перетирания пользовательских файлов, выставляет `NETSTITCH__DATA_DIR`, `NETSTITCH__CONNECTORS_DIR` и `NETSTITCH__INTEGRATIONS_DIR`, после чего core/module SQLite и module data остаются user-local.

- Какие интеграции должны быть изолированы от core runtime.
