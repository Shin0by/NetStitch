# Security NetStitch

## Базовые гарантии

- Секреты, токены, private keys и production credentials не коммитятся.
- Project-local секреты хранятся только в ignored local contour, например `.local/` и `.env.*.local`.
- Audit/event payload не должен содержать секреты.
- Внешние интеграционные модули выполняют запись только внутри явно выбранного module-owned/root-owned контура и собственного `integrations/<module>/data/`; core не должен требовать правки vendor-managed файлов внешнего продукта.
- Profile-aware экспорт внешнего модуля по умолчанию должен писать только module/NetStitch-owned generated files внутри resolved module root. Прямая правка выбранного profile/config допускается только в explicit advanced-режиме, а merge в существующие списки - только в explicit dangerous-режиме с отдельным подтверждением, block markers `NetStitch BEGIN/END` и отчётом changed files. Непокрытые `protocol + port` не должны получать автоматически скопированный метод обхода; для этого нужен отдельный advanced wizard/explicit flow. Backup является отдельной явной операцией перед экспортом: она перезаписывает одну project-owned backup-версию для всех файлов, которые текущий режим может изменить, и marker для файлов, которых не было до изменения; обычный export/apply не создаёт backup скрыто, а revert не удаляет backup-файлы/markers.
- Merge-export обязан защищать пользователя от self-deny правил: IP не добавляются в module-declared exclude/protected target sets, vendor-managed upstream lists и любые targets, классифицированные как исключающие или vendor-managed. Такие файлы остаются read-only для export engine, не попадают в список изменяемых файлов и отображаются только предупреждениями; запись выполняется только в module-declared positive target sets. Явный backup при этом создаёт копии всех файлов, связанных с matched rules, чтобы у пользователя был полный safety snapshot выбранного profile contour.
- Домены, введённые вручную в `Дополнительные настройки`, не являются секретами, но считаются пользовательскими routing-target данными: они не логируются отдельно, не отправляются во внешнюю сеть и записываются только в module-owned файлы при явном включённом domain-switch.
- Export preview не должен писать файлы. Export apply должен отклонять absolute/outside-root пути, path traversal-подобные значения и любые попытки записи вне resolved module root.
- WinDivert FLOW backend используется только для локального наблюдения metadata-событий выбранных процессов; payload трафика не сохраняется.
- Connector discovery добавляет только metadata о локально найденных executable paths и не должен отправлять эти пути во внешнюю сеть.
- Проверка обновлений обращается только к публичному endpoint GitHub Releases текущего репозитория и отправляет стандартные HTTP metadata с `User-Agent`. В запрос не включаются client identifier, web key, cloud session/JWT, Google metadata, monitoring rows, локальные пути, SQLite-данные, connector manifests или module state. Обновление не скачивается и не запускается автоматически: UI только показывает кнопку `Обновить программу`, которая открывает страницу GitHub Release/Downloads в системном браузере.
- Runtime connector apps `apps/*.app` являются декларативными manifest-файлами: приложение не исполняет код из них, не загружает DLL/script-плагины и использует только локальные discovery rules.
- Portable `storage\` хранит SQLite/cache/export state рядом с приложением; этот каталог является runtime state и не должен коммититься или попадать в source repo.
- Основная SQLite БД `storage\netstitch.sqlite3` не является storage-контуром внешних модулей. Module root, provider/download state, profile export UI state, module cache и generated metadata должны храниться только в module-owned `integrations\<module>\data\module.sqlite3` или соседних module-owned файлах внутри `integrations\<module>\data\`.
- SQLite `app_settings` хранит project-local пользовательские параметры вроде `ui.language`, `ui.enable_all_overlay`, `ui.monitoring.public_ip`, `ui.remember_window_placement`, `ui.window_*`, `ui.window_hidden`, `web.localhost_enabled` и публичный cloud upload nickname `cloud.upload.nickname`. Для cloud account допускаются только безопасные metadata вроде `cloud.auth.provider` и `cloud.auth.provider_subject_hash`; NetStitch session token, client private key и локальные display-only поля Google name/email можно хранить только как Windows DPAPI-защищённые blobs до явного выхода пользователя. Google email/name могут быть возвращены Worker-ом в ответе успешного OAuth только текущему клиенту для отображения в UI, но Google access token, OAuth client secret, session token, private keys, пользовательские пароли, Google email/display name/raw subject и provider credentials в открытом виде в SQLite не записывать. Obsolete keys `cloud.auth.login`, `cloud.auth.email`, `cloud.auth.display_name`, `cloud.auth.password.dpapi.v1` и `cloud.auth.stay_signed_in` должны быть удалены или мигрированы после перехода на Google OAuth. Кнопка `Выход` в cloud overlay должна удалить локальный session/client state, DPAPI-защищённые Google name/email blobs и obsolete auth keys сразу, без ожидания перезапуска; публичный `cloud.upload.nickname` не является auth secret и не удаляется при обычном выходе из Google-сессии.
- SQLite `ignored_addresses` хранит только пользовательские и автоматически сидированные IP/CIDR правила скрытия наблюдений, включая loopback и локальные IP текущей машины; это runtime metadata, не secret storage.
- Автоопределение локального IP для `ignored_addresses` и footer DNS/network indicator используют только публичные DNS/anycast IP как route/reachability probe targets; executable paths, observations и секреты туда не отправляются. В auto-seed попадают только IP, возвращённые ОС как локальный source address, после фильтра special/transition ranges вроде Teredo и 6to4.
- Список network endpoint probe targets хранится во внешнем editable `config\endpoint_probe_targets.txt` или передаётся через `NETSTITCH__ENDPOINT_PROBE_TARGETS` / `NETSTITCH__ENDPOINT_PROBE_TARGETS_FILE`; entries поддерживают `host:port` и `protocol://host:port`, а desktop/browser snapshot requests передают target и protocol отдельно. Native network tool module не содержит встроенного списка таких адресов и проверяет только targets, переданные caller-ом.
- Browser shell на корне уникального порта `https://<local-ip>:46473/` выключен по умолчанию и включается только через desktop switch `Web localhost` или стартовый default `NETSTITCH__WEB_UI=1` до появления persisted-настройки; `/web` и app-name path не публикуются; default watcher bind выбирает локальный IP машины для LAN-доступа и падает на localhost только если IP определить нельзя. `/v1/web-url` возвращает URL с `#web_key=<derived-key>` fragment, построенным из локального client identifier через отдельный hash-derivation; fragment не отправляется в GET, browser JS передаёт ключ POST-запросом в `/v1/web-auth`, получает HttpOnly SameSite cookie и удаляет fragment из адресной строки. Если открыть только IP и порт без ключа, browser shell показывает key prompt. Browser API отклоняет чужой `Origin`/`Referer`, не отдаёт permissive CORS headers, требует web-auth cookie для command/API routes и пишет audit-события remote browser actions без секретов. Desktop UI продолжает использовать отдельный internal client header и не зависит от browser cookie.
- Browser shell HTTPS использует app-owned самоподписанный сертификат `storage\web-server.cert.pem` и private key `storage\web-server.key.pem`; это защищает LAN-трафик после ручного доверия сертификату в браузере, но не является публичным CA identity. Диагностический fallback `NETSTITCH__WEB_SCHEME=http` допустим только для локального troubleshooting.
- Browser shell filesystem picker является частью того же opt-in LAN surface: routes `/v1/filesystem/browse`, `/v1/filesystem/read-text` и `/v1/filesystem/write-text` показывают/читают/пишут файлы машины, где запущен watcher, для явных UI-действий выбора executable, profile export и CSV import/export. Эти routes доступны browser shell только после web-auth gate; их нельзя использовать для secrets и нельзя считать полноценным remote file manager.
- Git push contour использует отдельный project-specific GitHub Deploy key, а не shared personal key. Private key хранится только в пользовательском `~/.ssh`, не коммитится и не копируется в workspace; public key можно публиковать как write-enabled Deploy key только для нужного репозитория. `known_hosts` должен пополняться только official GitHub host keys из `https://api.github.com/meta` или эквивалентного official source; fallback через `ssh.github.com:443` допустим, если стандартный SSH порт недоступен.
- Embedded watcher runtime работает через app-owned runtime boundary внутри `NetStitch.exe`. Любой будущий automation/headless entrypoint должен заново пройти security review и сохранить базовые правила: не передавать секреты, не логировать credentials и не расширять LAN surface без отдельного gate.
- Browser shell не должен читать локальные иконки через `file://`; watcher отдаёт только embedded UI assets и app icons, привязанные к существующим `tracked_apps` и лежащие внутри project-owned `apps\icons`, иначе возвращается безопасная default-иконка.
- IP enrichment выполняется только через native network tool module и не входит в hot snapshot/render path. Модуль может обращаться к внешним DNS/WHOIS источникам для диапазонов и DNS resolve домена в явной команде `lookup-domain`, поэтому он должен хранить только public IP/range metadata в SQLite cache, не отправлять локальные executable paths и не блокировать core runtime при сетевых ошибках. Домены monitoring rows допускаются только из payload-level источников `http_host`/`tls_sni`/`quic_sni` или из доверенного CSV import.
- Будущий community cloud sync должен быть полностью opt-in per action: NetStitch не выполняет cloud-запросы на startup/bootstrap, snapshot refresh, render path, открытие окна `Информация` или фоновым polling. Открытие cloud overlay считается явным действием пользователя и может выполнить один стартовый refresh доступности, quota upload/download и server-side списка приложений; пока overlay открыт, автоматический refresh этих данных каждые 10 секунд также считается частью этого явного действия. Повторный render overlay сам по себе не делает network request. Browser shell не обращается к внешнему Worker напрямую: весь cloud import/export web-контур ходит только в локальные `/v1/cloud/*` routes embedded watcher runtime, а уже native runtime выполняет внешние запросы в рамках явного cloud-действия. Refresh/status cloud HTTP-запросы UI используют общий deadline `9.5` секунд из 10-секундного overlay-цикла и не применяют устаревший refresh-result поверх более свежего sign-in/sign-out; interactive auth/upload/download операции не должны наследовать короткий refresh-timeout. Public download разрешён без аккаунта, но upload разрешён только после входа через Google OAuth в overlay и успешной server-side captcha/rate-limit/browser-verification policy. Пользовательский пароль NetStitch не принимает и не хранит; Google OAuth access token используется только для server-side verification/exchange и не сохраняется локально. Worker сохраняет в одноразовом OAuth-state только безопасную локаль UI, чтобы промежуточные browser-страницы отображались на том же языке, что и приложение. Google OAuth start дополнительно ограничен отдельным server-side bucket: 5 стартов за 15 минут на hashed client/IP/UA bucket; это не расходует лимит неудачных входов. Server-issued SVG captcha хранит в D1 только salted hash ответа, purpose/scope, TTL и счётчики попыток; открытый ответ не логируется и не возвращается клиенту. Перед Google redirect Worker также требует state-bound browser verification: SHA-256 proof-of-work, короткий memory-walk, canvas/WebGL/storage/language/timezone/screen/Worker/timing сигналы и лёгкий interaction trail. Координаты pointer/click внутри кнопки отправки передаются только в процентах и используются как risk-сигнал при отсутствии координат, 0/100%, углах или идеально центральном клике; это не поведенческая биометрия и не единственный hard fail. Upload должен использовать session/client key + JWT. Refresh, quota check, Google OAuth start/callback/poll, captcha verification, browser verification, upload и author-scoped download допускаются только после явного действия пользователя внутри overlay или будущего явно утверждённого automation entrypoint. Локальный quota/client state может отображаться из SQLite cache без сетевого запроса.
- Публичное авторство cloud upload является отдельным user-controlled surface. Поле `Никнейм` в UI обязательно, не должно автозаполняться Google display name/email и принимает только whitelist `A-Z`, `a-z`, `0-9`, `!.@#$%^&*()_+=-~` длиной до `32` символов. Worker обязан проверять ник server-side, хранить normalized case-insensitive форму для уникальности, отклонять только явно зарезервированные/служебные ники вроде `root`, `admin`, `support`, `system`, `official`, `netstitch` в любых регистрах, и привязывать ник к конкретной Google OAuth identity через необратимый provider subject HMAC с server-side secret `NETSTITCH_IDENTITY_PEPPER`. UI может проверять доступность ника через endpoint Worker после debounce `1.5s`; этот endpoint возвращает только состояния accepted/taken/invalid/blocked и не раскрывает чужую Google identity. Если ник уже привязан к другому provider subject hash, upload/claim отклоняется без раскрытия чужих identity details; разные Google accounts при этом считаются разными author identities и могут иметь разные ники. Смена ника владельцем должна обновлять только author profile/current signature, а не копировать ник в observation rows; старые публикации этого автора в публичной выдаче и поиске должны переходить на нового `Автора` через join по стабильному author id. Google email/display name/raw subject не должны использоваться как публичный author field, поисковый ключ или обратимо хранимый cloud identity field. Сырой email/name допустим только как поле ответа OAuth `session` для текущего клиента и как локальный Windows DPAPI-защищённый display blob; Worker хранит только HMAC-значение `email_hash`, а публичные API, CSV export, logs и monitoring rows не должны раскрывать email; для identity matching использовать provider subject hash/client id.
- Локальный monitoring storage и CSV export/import являются privacy boundary: они не должны содержать author signature, Google email/display name, provider subject, user id, client id, session id, cloud privacy marker или любые данные пользователя. При переносе cloud rows в monitoring или CSV публичная подпись автора и признак приватности отбрасываются; приватность допустима только внутри cloud upload/download API, cloud D1 namespace и cloud import staging UI.
- Worker upload endpoint требует две независимые проверки: `Authorization: Bearer <session_token>` для пользователя и `x-netstitch-jwt` ES256 подпись активным client key для scope/body/TTL/replay. Upload JWT TTL ограничен 15 минутами, `body_sha256` должен совпадать с raw body, а `jti` пишется в replay cache.
- Cloud quota operation ids являются техническими идентификаторами одной пользовательской upload/download операции. Worker хранит их в `client_quota_operations` только вместе с privacy-preserving `client_identifier`, видом операции и временем конца quota window; endpoint rows, cloud account secrets, Google data, ники авторов и monitoring payload туда не записываются. Повторные страницы/пачки с тем же `operation_id` не расходуют quota повторно, но всё равно проходят auth/JWT/body validation для соответствующего endpoint.
- Доверенность cloud observations не повышается из-за одного имени приложения. Verified upload возможен только когда клиент прислал локально собранный stable app identity key для текущего приложения; сервер не требует заранее заведённый список разрешённых издателей. Stable app identity key строится из всех доступных стабильных доказательств: валидный Authenticode leaf SPKI, если он есть, плюс Windows VersionInfo `CompanyName` и `ProductName`; все значения перед хешированием нормализуются в нижний регистр, а версия, путь и имя exe не входят в ключ. Для неподписанных приложений отсутствие Authenticode не является автоматическим отказом, если есть стабильные VersionInfo-поля; при появлении Authenticode у того же продукта ключ станет другим и будет считаться другой verified-идентичностью. Worker пополняет `app_catalog` из authenticated upload payload и может отклонять только явно заблокированные `app_id`. CSV/imported данные с отсутствующим или несовпадающим evidence отправляются только как `CloudImportUntrusted`. Импортированная подпись сохраняется как provenance строки и не заменяется подписью локального executable; в D1 `publisher_key` входит в primary key для provenance и защиты от конфликтов записи, но public/private cloud rows наружу схлопываются по `app_id + IP + port + protocol`, чтобы Monitoring, CSV и cloud download имели общий логический принцип уникальности. Приватный/author-scoped срез остаётся отдельным privacy namespace и не становится частью локальной строки.
- Cloud D1 observations должны удаляться по retention policy не позднее 365 дней от `last_seen_ms`/`last_observed_at`. Cleanup не является пользовательским purge и не должен удалять пользователей, ключи, app catalog или audit events; audit payload не должен включать секреты.
- Operator cleanup облачной D1 имеет две явные области. `scripts\clear_cloud_database.ps1 -Scope AppData -Yes` удаляет только данные приложений и наблюдений (`app_catalog`, `observations`, `observation_author_rows`, `observation_submissions`, `domain_verifications`) и сохраняет users, client identifiers, sessions, keys, authors, OAuth/captcha/rate-limit/browser-verification states, quota windows, audit rows, D1 schema/migrations и service metadata. `scripts\clear_cloud_database.ps1 -Scope All -Yes` остаётся отдельной разрушительной процедурой для полного обнуления клиентского следа: она удаляет все users, client identifiers, sessions, keys, authors, app catalog, observations, OAuth/captcha/rate-limit/browser-verification states, quota windows, audit/cache rows и любые данные, переданные клиентами или созданные вокруг клиентских действий, сохраняя только schema/migrations/service metadata.
- Расширенный мониторинг использует WinDivert FLOW/NETWORK только в sniff-режиме для UDP/QUIC endpoint-событий, исходящих TCP payload-пакетов и UDP/443 QUIC Initial. Payload не сохраняется в SQLite, логи или audit, а после разбора отбрасывается; сохраняются только endpoint metadata и, если удалось доказать, нормализованный домен, источник (`http_host`, `tls_sni` или `quic_sni`) и ключ строки наблюдения. Если WinDivert capture недоступен, обычный мониторинг IP/портов продолжает работать без UDP/QUIC-сокетов и без доказанных доменов.
- WHOIS/range cache ограничен `1000` строками с ротацией, чтобы runtime SQLite не рос бесконтрольно из-за внешних lookup-данных.
- Module provider download является явным пользовательским действием, выполняется только кодом выбранного модуля, сохраняет данные внутри `integrations\<module>\data\`, использует zip/path traversal protection и затем проходит module-owned root detection перед применением.
- Module UI action boundary допускает только локальные host-команды: фильтры, monitoring start/stop, tracked apps, monitoring rows, module-owned background task control, host-owned `browse_window` для выбора пути, module event logging и стандартные module dialogs. Live-события `IntegrationHostEvent.event = "ui_values"` во время долгого `ui_action` могут менять только явно названные host-owned UI state keys текущего модуля; host не маппит `download_progress` или другие внутренние события на module UI ids. `browse_window` возвращает только выбранный путь в UI state модуля и не читает, не создаёт, не импортирует, не экспортирует и не перезаписывает файлы от имени host-а. Фоновые задачи модуля не имеют autostart при запуске NetStitch или загрузке manifest и стартуют только после явного пользовательского действия. Модуль может получить выбранные локальные строки мониторинга и сохранить их в собственной `integrations\<module>\data\module.sqlite3`, но не получает команд для cloud upload/download, CSV import/export, cloud credentials, Google metadata, session tokens или прямого доступа к основной SQLite БД.
- Готовые архивы SDK-примеров в `docs/module-sdk/packages/` являются tracked developer artifacts из tracked исходников `docs/module-sdk/examples/`; они не должны содержать runtime `data/`, локальные БД, секреты, `.local`, `target`, `build` или temp-каталоги. При изменении примеров архивы пересобираются project-owned скриптом `scripts\package_module_sdk_examples.ps1`.
- `scripts/check_secrets.ps1` выполняет high-confidence проверку tracked и неignored untracked text files на private key blocks и распространённые token formats перед обычным dev check.
- Signing contour не должен хранить private keys, PFX/P12 passwords, hardware token PIN или provider API tokens в tracked-файлах; tracked допускает только безопасный шаблон `config/signing.example.toml`.
- Self-signed signing certificate не является production trust; если он используется для release artifacts, статус релиза должен явно отмечать test-signed подпись.
- `scripts/sign_windows.ps1 -EnsureTrustedForCurrentUser` импортирует публичную часть test-сертификата в пользовательские Windows certificate stores; этот флаг нельзя использовать неявно или как часть обычного compile/package path.
- Статус подписи `UnknownError` для self-signed сертификата без trust-store импорта допустим только в development-контуре и не должен трактоваться как production-ready подпись.
- GitHub portable release workflow использует только стандартный `GITHUB_TOKEN` для создания tag/release и не должен требовать project secrets для обычной сборки. Push в `release` запускает workflow `Portable Release`; после успешной сборки публикуется GitHub Release. Ветка `main` не участвует в текущем release/security contour. Ручной workflow `publish_release=true` допустим только для явно подтверждённого повтора или аварийного запуска, если штатный release-branch push не смог быть использован. Перед публикацией release assets workflow обязан собирать clean staging-copy, исключающую runtime SQLite, пользовательские connector manifests/cache, temp и local secret contours. Локальный generated `dist\...\config\version-manifest.json` не попадает в git; для публичного deploy коммитится только безопасный `config\release-version.json` с tested full-version без secret/runtime данных.

## Threat Model на старте

После появления runtime-модулей главные риски связаны с границами загрузки локальных shared libraries и с процессом разработки:
- утечка секретов через git
- логирование чувствительных данных
- неявная зависимость core runtime от внешней сети
- отсутствие документированных recovery и verification paths
- чрезмерно широкий мониторинг сети вне выбранных пользователем процессов
- повреждение локальной папки внешнего продукта небезопасной интеграцией
- запуск UDP/QUIC мониторинга требует админ-прав и доверенного локального WinDivert runtime из ожидаемого источника
- portable packaging не должен подтягивать WinDivert или другие runtime-бинарники из сети автоматически; WinDivert-файлы берутся из явно указанного локального trusted path (`NETSTITCH__WINDIVERT_DIR`, `NETSTITCH__WINDIVERT_DLL`) или из tracked project-owned runtime payload `resources\runtime\windivert\windows-x86_64`, а интеграционные native libraries (`.dll`/`.so`) и их content не входят в core package по умолчанию и копируются только при явном выборе модуля из tracked/current `integrations\<module>\` или пользовательской portable-папки модуля
- пользовательские connector manifests могут раскрывать локальные пути в UI/SQLite, но не должны содержать секреты, токены или credentials
- portable-папка может содержать локальные пути и наблюдения в SQLite; при передаче пакета третьим лицам runtime `storage\` надо рассматривать как пользовательские данные
- утечка signing private key или PFX password через git является критическим инцидентом; реальные signing-файлы должны храниться в ignored `.local/signing/`, `config/signing.local.toml` или внешнем secret storage
- публикация release-артефактов с self-signed сертификатом без явной маркировки test-signed статуса считается release/security incident
- случайная публикация release-артефактов с локальной runtime SQLite, пользовательскими connector manifests/cache или temp/local secret contours считается release/security incident
- включение browser shell или watcher bind на non-loopback адрес без HTTPS/web-key gate, same-origin/CSRF gate и audit remote actions считается security risk
- возвращение watcher/helper child process transport без отдельного review считается локальным trust-boundary risk; embedded runtime снижает process-boundary поверхность, но не заменяет проверку команд, auth/session policy для web surface и отсутствие секретов в payload
- автоматическая или фоновая загрузка внешнего продукта модулем из сети без клика пользователя считается security risk; background task модуля должен быть остановимым через host и не должен стартовать сам при запуске приложения
- community cloud contour не должен хранить обратимые Google email/name/raw subject; публичный автор задаётся отдельным `Никнейм`, привязанным к необратимому Google provider subject hash и проверяемым server-side на case-insensitive уникальность
- cloud upload требует одновременно Bearer session и ES256 `x-netstitch-jwt` с body hash/scope/TTL/replay protection; download публичен только для общего `app_id`-среза и расходует cloud-side quota по privacy-preserving client identifier
- CSV/local monitoring storage не содержит ник, email, provider subject, user id или client id; cloud staging export/import отбрасывает author metadata и переносит только endpoint/app/signature provenance

## Требования к логированию и аудиту

- Использовать системные и стабильные `action_type`.
- Для runtime-ошибок добавлять correlation/request id там, где это применимо.
- В audit log хранить системные поля: `event_id`, `created_at`, `entity_type`, `action_type`, `entity_id`, `actor_id`, `payload`.
- Локальный UI/runtime log хранится в SQLite `system_events` с системными `source`, `component`, `action_type`, `severity`, `entity_type`, `entity_id` и JSON `payload` без секретов. `source = core` используется для host/runtime событий, `source = system` - для системных UI-событий, а source внешнего модуля берётся из его отображаемого имени manifest. `core` и `system` зарезервированы регистронезависимо для `id` и `display_name` модуля, чтобы модуль не мог маскироваться под host/system contour. Severity принимает только `info`, `success`, `warning`, `error`. Footer `Message` читает последние события из этой таблицы, copy-history берёт последние 100 строк, а одинаковые подряд события схлопываются через `repeat_count`. Таблица ротируется до 9999 строк, чтобы лог не создавал бесконтрольную нагрузку и рост portable storage.
- Portable packaging может поставить локальный marker `storage\clear-system-events-on-next-start`; первый запуск после сборки удаляет только строки `system_events`, чтобы новая тестовая сборка не смешивала старую историю сообщений с текущими событиями. Marker не удаляет observations, tracked apps, cloud session, настройки или другие runtime-таблицы.

## Текущие риски

- Cloud auth MVP определён как Google OAuth + server-side captcha/browser verification + ES256 client request JWT; дальнейший hardening требует live-smoke и abuse/rate-limit review перед публичным релизом.
- Audit/event контур для локального UI/runtime закреплён через `system_events`; отдельный production audit contour для будущих remote/operator событий может быть расширен позже без логирования секретов.
- Автоматическая high-confidence проверка секретов добавлена в tooling, но не заменяет ручной review новых release/signing/cloud contours.
